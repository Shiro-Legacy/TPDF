## /ToUnicode CMaps with Flate damage (major: edit-targets, edit-text, edit-replace-preview, edit-replace-apply)

- **Verified** on ed62a16 with the reviewer's p21 and p22: an Identity-H font whose /ToUnicode has an EOL inside /Length (LF or CRLF), a wrong Adler-32 or none lost its code map, so its runs were `unsupported-encoding` (or `subset-font`); MuPDF lists them as candidates. A coded simple font the same.
- **Fix** (`edit/font.rs` `read_bounded`): the strict decode first; when it refuses the stream as invalid, `edit::decode_lenient`, which is the new `stream_object::decode_document_stream_lenient`: the strict metadata rules with Flate as tolerant as MuPDF's (`stream::decode_filter_specs_lenient`, which repair already uses: data after the zlib end ignored, the bytes before a bad or missing checksum or a truncation kept). It decodes within the same room and is charged to the scan's 2 MiB. A stream over the room stays unproven. Other damage (LZW, an unknown filter) still leaves the font unproven. The view's decode (hayro-syntax) is not used here: it has no output bound.
- Tests: `an_identity_h_cmap_with_flate_damage_is_read_as_mupdf_reads_it` (fixtures/p0b/edit-embedded.pdf) and `a_coded_font_cmap_with_flate_damage_is_read_as_mupdf_reads_it` (edit-coded.pdf). Each takes four damaged variants of the fixture's own CMap in an appended update and checks four things: the strict decoder refuses it; the scan's verdicts and repertoires equal the clean file's; edit-text and its undo restore every byte; edit-replace-preview and edit-replace-apply (1 and 2 matches) and their undo do too.
- Measured: p21 and p22 now match MuPDF in every variant, and the saved pixels are identical. On the reviewer's 12 corpus files (govdocs1 000592, 000629, 000753, 000630, 000324, 000367, 000280, 000272, 000177, 000562, 000746; pdf.js issue11651), the first three pages of each now give identical edit-targets verdicts (4,085 items) and identical outcomes for 115 edit-text requests. On ed62a16 the same probe found differences, for example 259 items and 1 edit in 000177 a92188dd5fa8, and 3 items and 1 edit in issue11651 dbbe8b9a3763.

## Content streams no decoder reads (minor: edit-targets, text-add)

- **Verified** on the reviewer's inputs: qpdf bad-data.pdf, split-exp-1.pdf, broken-lzw.pdf and bad-data-out.pdf (LZW without a clear code), and pdf.js bomb_giant.pdf (JBIG2Decode on /Contents). Each refused the whole page `invalid`, text-add included. MuPDF reads these streams as empty, and the view draws nothing from them.
- **Fix** (`edit/walk.rs`): a stream the strict decoder refuses is still read as the view reads it. A stream the view cannot read either is now empty: it holds no targets and is never written. hayro's page content skips such a stream, so this is what the view draws. A content stream with an image filter (JBIG2, JPX, DCT, CCITT; `app::view_contents::encodes_samples`, now `pub(crate)`) is empty without being decoded, because the view leaves it out. Before, the scan's view fallback decoded bomb_giant's JBIG2 streams whole. Page 0 of bomb_giant now scans in 34 ms with a 132 MB peak (2 items, as MuPDF), and text-add takes 7 ms. On ed62a16 the page was refused after 122 ms with a 1,125 MB peak.
- A filter name no reader knows (`/FooDecode`) was already, and is still, read raw by the view, as MuPDF does, so its runs are listed.
- Messages print an unknown filter as a name: `unsupported filter name /JBIG2Decode`, with bytes outside the printable range as `#xx` (`stream_object.rs`). ed62a16 printed a byte list.
- Test: `a_content_stream_no_decoder_reads_holds_no_targets`. It checks [LZW junk, text, JBIG2 junk, /FooDecode text]: the scan lists the two readable runs; edit-text and text-add work and keep the unread streams' raw bytes; two undos restore every byte. It also checks a page whose only stream is LZW junk: 0 items, and text-add works.
- Measured: the four qpdf files now scan `ok 0` on both engines and text-add works on both, as on MuPDF.
- **Difference, recorded instead**: pdf.js PDFBOX-4352-0.pdf ede76ce3aaa8 has a Flate stream without a zlib header. MuPDF reads it as empty. The view (hayro, like pdf.js) reads it as raw deflate, and the bytes contain one the scanner cannot follow (`{`). So edit-targets and text-add still refuse `invalid` there. Both engines render the page blank. This is kept: the scan reads what the view reads, and refuses a page whose content it cannot follow instead of guessing.
- **Same exposure outside this group, routed and not changed here**: redaction's content walk (`redact/content.rs`), `redact/verify.rs` and `redact/images.rs` also fall back to `ViewDocument::decoded_stream` with no image-filter check. On bomb_giant, redact-preview and redact-apply refuse after about 1.3 GB (peak RSS). The same `encodes_samples` guard before that fallback would avoid it.

## Generated CMap and /W codes per scan (minor, hostile cost)

- **Verified** on ed62a16 with the reviewer's p27b: 64 fonts share one 600-byte CMap and /W, each expanding to 2^20 codes. edit-targets took 14.5 s.
- **Fix** (`edit/font.rs`): a scan expands at most `MAX_SCAN_CMAP_CODES` = 2^21 codes in all (2^22 since round 2). That is one font at both of engine.ts's per-font ceilings (2^20 CMap, 2^20 /W), so no single font engine.ts proves is lost. The count is kept in `Budget::codes`. bfrange and /W range codes count against both the per-parse ceiling and the scan total. /W array entries count against the total only, because a shared /W array costs every font that names it. A parse past either ceiling charges nothing and leaves its font unproven, as the per-font ceiling did.
- **Found while verifying**: every run of a proven font carried its own copy of the font's widths (up to 65,536 entries) in `CidWrite`. 512 short runs of one font with a full /W range held 512 copies. `Cid::widths` and `CidWrite::widths` are now one `Arc` per font.
- Tests: `generated_cmap_and_w_codes_are_charged_to_the_scan` uses three Type0 fonts sharing a descendant whose /W is 15 full ranges plus the fixture's own. The first font is proven and the other two are not; with the fixture's /W alone all three are. `the_runs_of_one_font_share_its_widths` checks 40 runs and one `Arc`. The unit test checks the totals and that a refused parse charges nothing.
- Measured with p27b, Rust, warm: 64 fonts 0.66 s (was 14.5 s; 1 candidate); 128 fonts 1.5 s (was 29.4 s and about 600 MB); 512 fonts 3.7 s at 760 MB peak. At 512 fonts the remaining time is the view's structured text: `search` on the same file also takes 3.7 s, because hayro parses each font's CMap. That cost belongs to the view.
- **Difference**: on such a page, the fonts after the total are unsupported (`unsupported-encoding`, or `subset-font` for a subset name), where engine.ts proved them at 30 s or more.

## edit-replace-preview after security-set (minor)

- **Verified**: security-set moves the session revision without a journal step, and the renderer's `applySecurityReply` did not rescan. So the next preview carried the old scan's revision and was refused `stale-target` until the user refreshed. On engine.ts, edit-text and edit-paragraph had the same problem, because `resolveEditTarget` compares the revision too. Only the preview differed between engines.
- **Fix** (renderer, both builds): `applySecurityReply` refreshes the content scan as `applyEdit` does (`refreshContentTargets(uiMode === "edit")`). The recorded engine check (§7 #10) is kept. It refuses a preview of another revision than the caller's scan, and the renderer now always holds the current one.

## Fonts whose /BaseFont is not ASCII (major: all five)

- **Verified** with p39, p40 and p42: runs in a font named with GBK, Shift-JIS, Latin-1 or valid UTF-8 bytes were `ambiguous-text-association`, so they could not be edited, rewrapped or replaced, and their paragraphs were not listed; engine.ts lists and edits them. Cause as found: `walk.rs` matched runs by `summary.name` (Latin-1 of /BaseFont), while the view names a run's font with hayro's `Name::as_str` (UTF-8, or the placeholder `{non-ascii key}`). The round 1 record calling the name display only was wrong.
- **Also found**: the view cuts the name at 31 bytes, as MuPDF's 32-byte font-name buffer does, and names a Type0 font by its descendant's /BaseFont. So a font named past 31 bytes (p39's `long` case; `ABCDEF+TimesNewRomanPS-BoldItalicMT` is 35) or a Type0 whose own name is not its descendant's (`X-Identity-H`, ISO 32000 9.7.6.1) was unassociated on both engines: engine.ts compared the same way against MuPDF.
- **Fix**: `Font::view_name` (`edit/font.rs`) is the name the view gives the font's runs: `view::text_font_name` (new, `view/stext.rs`, shared with `font_facts`) of the descendant's /BaseFont for a Type0 font, else the font's own. `walk.rs` matches runs by it. `summary.name` stays for display, now UTF-8 when the bytes are UTF-8 (`CaféSans`, `宋体`), else Latin-1 as before. `match_runs` treats an empty name as no filter, as engine.ts's truthiness check did.
- **Difference, deliberate**: names past 31 bytes and Type0 names other than the descendant's now associate, where engine.ts refused `ambiguous-text-association`. Corpus (pages 0-1 of the 4,956 files the probes open): 58 files have a font name past 31 bytes, 47 a Type0 named other than its descendant, 8 a non-ASCII name. On these 110 files, against round 1's classes: 34 files gain items that are candidates here and `ambiguous-text-association` on MuPDF, and 15 gain different preview sets; every one of the 186 support differences on the 110 files goes that way. The two non-ASCII files that refused edits (pdf.js issue20489.pdf b4f9dcbad293, veraPDF 6-1-7-t01-fail-c e69730958951) now match MuPDF; e69730958951 keeps a display-name difference (Latin-1 against U+FFFD). Of 59 newly associated runs edited on Rust (up to 4 per page): 55 edits land, 3 refuse `overflow` and 1 `read-only`; MuPDF reads 53 of the 55 back from the saved file; the other 2 are one kerned Type0 run of pdf.js b7f8ffae8ccd whose original text MuPDF's extraction does not show either (Rust's search finds the new text). Replace previews list these runs (as matches, or as rows rejected `overflow` or `shared-placement`).
- Tests: `simple_fonts_with_non_ascii_or_long_names_are_edited` (TrueType and Type1, nine names: GBK, GBK with `,Bold`, subset GBK, Shift-JIS, Latin-1, UTF-8 (two), 35 bytes, and 37 bytes cut inside `é`). ## The view's /W expansion (minor, p3-edit "/W expansion" timing)

- **Verified**: hayro (`vendor/hayro-interpret-0.8.0/src/font/cid.rs` `read_widths`, `read_widths2`) set every code of a /W range in a hash map. The U3 file's 200 ranges above 0xFFFF are 13M entries: edit-targets 0.56-0.63 s, search 0.55 s, render 1.2 s. **Also found**: `[0 4294967295 500]`, a few bytes, asks for 2^32 entries, so every view op on such a font runs out of memory (16M codes took 1 s and 646 MB in WASM).
- **Fix** (vendored hayro-interpret, recorded in its PATCH.md): /W and /W2 set CIDs up to 0xFFFF only (CIDs are two bytes; MuPDF keeps these ranges as 16-bit pairs) and at most 2^18 codes per array, the rest of the array ignored. A real font sets each of at most 65,536 CIDs about once.
- Test: `w_ranges_past_two_bytes_cost_the_view_nothing` (U3's 200 ranges, then those after `[0 33554431 500]`): edit-targets and search under 500 ms each case. On pristine hayro the first case alone took 810 ms native.
- Measured with p38 on the U3 file: Rust edit-targets 10-19 ms, search 2-29 ms, render 7-15 ms (MuPDF about 340 ms each).
