# Dynamic XFA forms (materialized at open)

November 4, 2026; scripts added November 5, add-row and delete-row buttons November 5, picture clauses November 5, FormCalc lists, dates and finance November 5. Code: `src/xfa/`. Hooks: `app::document::AppDocument::load` (open), `app::ops::fields::relayout` (fill). Tests: `tests/app_xfa.rs`, unit tests in each module. Bench: the owner's `Status_Certificate.pdf` (Adobe Designer 6.5, AEM Forms; a copy and its packets are in `tpdf-wt/scratch/xfa/`; it is not a fixture and never enters the repository).

## The problem

A dynamic XFA form (`/NeedsRendering true`) carries one placeholder page ("requires Adobe Reader 8 or higher") and the real form as XML packets in /AcroForm /XFA: a template (layout, fields, captions, rich text, scripts), datasets (the values), config and locale set. Only Acrobat and Reader lay the template out. Every other viewer shows the placeholder. The app opened such files view-only and showed the placeholder with a banner.

## Decision: materialize, do not render

At open, the app lays the template out itself and writes a new, ordinary PDF: one page per laid-out page, the static content drawn in page content with base 14 fonts, and a widget annotation (an AcroForm field) for every fillable field. That document becomes the session's live document. Everything downstream works unchanged: the view, text and search, the fields panel, fills, appearance synthesis, undo, save. No viewer-side XFA rendering exists; the render path never learns about XFA.

The materialized document keeps the XFA packets (the `form` packet, Acrobat's cached form DOM, dropped) and `/NeedsRendering true`. So:

- Acrobat and Reader ignore our pages and lay the form out from the template and datasets, as before.
- Every other viewer shows our pages and our widgets.
- A fill here is written to the widget's /V and, in the same journaled step, into the datasets packet (`sync`), so Acrobat shows what was filled here, and undo restores both.
- A reopen of a saved file sees the catalog marker `/TPDFXfa 1` and keeps the pages as they are (annotations and fills survive); it does not lay out again.

## Scripts: run where Acrobat runs them

Designer forms carry JavaScript in `event` elements, in the `calculate` and `validate` properties of fields, groups and subforms, and in `variables/script` objects; the bench form has 377 of them and 205 `presence="hidden"` nodes, and a choice of condominium type reveals whole sections. `src/xfa/script/` runs the subset such forms use (`parse` reads the JavaScript; `eval` runs it against the bound form; `formcalc` reads and runs FormCalc through the same runner; `script/mod.rs` picks the events):

- **At open** (`materialize`), after binding and before layout: every `initialize` event in document order (a node before its children), then the `ready` events (`$form`, then `$layout`). That is what Acrobat fires at open, and Designer forms reproduce their saved state from the data in those events (the bench form keeps an `initFld` flag and switches to its `*ShowHide` functions once set). `change`/`click` handlers do not run at open: Acrobat does not run them, and in the bench form they reset other fields (`NotCommon()` clears Section 6's boxes), so running them for every stored value would lose fills.
- **Calculations**, after the open-time events and again after a fill's handlers: every `calculate` script in document order sets its node's value to the script's completion value (the value of the last statement when it is an expression; a script that assigns `this.rawValue` itself and ends otherwise keeps what it set; an empty or `null` result empties the field). When a pass changed a value, one more pass runs, so a total that reads another calculated field settles; never more than two (Acrobat iterates until nothing changes; a form whose calculations need a third pass shows the second's values).
- **Validations**: after a fill's handlers, the filled node's `validate` scripts run, so what they set stands, but their result is dropped: nothing tells the user a value failed validation yet, and the value is kept either way.
- **On a fill** (`field-set` on a materialized form), after the datasets packet took the value: the form is built again from the updated packets, `initialize` and `ready` run as at open, then the filled node's own handlers (`click` and `change` for a check box or a radio group and its chosen button; `change` and `exit` for anything else, `xfa.event.newText` the value). The result replaces the live document whole (`Transaction::replace_with`: every object put or removed, the trailer's /Root moved) in the fill's journaled step, so undo brings the previous pages and widgets back and redo the new ones. Widget object numbers change when that happens; the fields panel refetches after every edit.
- **When nothing the layout shows changed**, the pages stay: the emitter writes `/TPDFXfaSig`, a hash (`xfa::signature`) of every node's presence and access, every draw's value and the values of non-fillable and floating fields. A fill whose rebuilt state has the same signature, and whose scripts set no fillable field, is `Materialized::Unchanged` and keeps the document as it is (typing a name costs no relayout and no new widget numbers).
- **Add-row and delete-row buttons** (`materialize_after_click`). A push button with a `click` event (`Field::clickable`: a `button` ui, not read-only, not inactive) gets a widget over its whole box: `/FT /Btn` with the push-button flag (`/Ff` bit 17), no /V, no `TPDFData`, its SOM name in `/TPDFSom` (`xfa::CLICK_KEY`), its tooltip (else its caption) in /TU, no /MK (the caption is drawn in the page content, as for every XFA border). The `fields` op lists such a widget (only such: other push buttons stay unlisted) with kind `button`, its /TU as the label, an empty value; `field-set` on it, whatever the value, is a press: one journaled step (`fill field`) that builds the form again as a fill does (`initialize`, calculations), runs the button's `click` handlers, and applies the `instanceManager` operations they asked for. Those are recorded, not done, by the runner (`Runner::take_instance_ops`): `addInstance` (one blank instance after the last), `removeInstance(i)`, `setInstances(n)` (adds or removes at the end), each refused silently past `occur` min or max (`limits::MAX_INSTANCES`, 1,024, for an unbounded max), or when the subform's instances are not bound to data groups of their name under one parent; `count` includes what was recorded, `index` is the instance's. `sync::apply_instance_ops` applies them to the datasets packet (the values the scripts set written first; every instance's group made where missing, then an empty group inserted after the last of the name, or the `i`-th removed), the form is bound to the result and its `initialize` events and calculations run once more (operations those ask for are dropped: one re-bind per press), then the layout. The result is always `Written` when an operation applied (the rows changed); a press that changed nothing (a delete at `occur` min) is `Unchanged` and records no step. Undo brings the previous rows, values and datasets back as for any fill. A fill's `change`/`exit` handlers apply their instance operations the same way. Operations asked for by the open-time events and calculations are dropped: the form is built again from the data at every fill, so a row an `initialize` event adds would be added at every fill. The Mac app's Fields panel lists the button (`FieldKind::Button`, titled by its field name and caption: "Add · +"); selecting the row, clicking the button on the page, or Enter or Space on it presses it.
- **Values scripts set** on bound fields (`initFld`, the floating "unit"/"Parcel" words) are written into the datasets packet of the materialized document (`emit::Extra::datasets`), as Acrobat's data DOM would hold them, so the next rebuild and Acrobat see them.
- **What runs**: `this`/`xfa.event.target`, `rawValue`/`value`, `presence`, `access`, `isNull`, `name`, `parent`, `index`, `instanceManager` and `_Name` (`count`, `min`, `max`, `addInstance`, `removeInstance`, `setInstances`, recorded as above; `moveInstance`, `insertInstance` do nothing), `xfa.resolveNode` and `resolveNodes` (`script/som.rs`, below) with `name`, `name[n]`, `name[*]`, relative indexes, `..name`, `*`, `#class[n]`, `parent`, `xfa.form`, `$form`, `$record`, `$data`, `xfa.datasets`, `!name` (`resolveNode` gives the first node named; `resolveNodes` a list with `length`, `item(i)` and `[i]`, so `for (var i = 0; i < l.length; i++)` runs over it; a predicate names nothing) (a `#class[n]` step counts in the scope of the nearest named node at or above the cursor: its children in document order, each unnamed subform followed by its own; so the bench form's `Section22.#subform.#subform[2]` is the unnamed subform holding `Subject`); names resolved as XFA scopes them (the node's children, then each ancestor's children and variables, unnamed subforms transparent; a script object's functions resolve from the subform holding its `variables`); `var`, `if`/`else`, `switch`, `while`, `do`, `for`, `return`, functions, the arithmetic, comparison and logical operators with JavaScript's conversions, a few string and number methods. `xfa.host` members are functions that return `undefined`.
- **FormCalc** (`script/formcalc.rs`), XFA's default language, so every script without a JavaScript `contentType` (an unset one included): its own lexer (`;` and `//` comments, `""` inside strings), reader and evaluator, with names, SOM steps, members, `resolveNode`, values and presence going through the JavaScript runner, so both languages resolve a name the same way. Runs: references (`Name`, `Name[n]`, `A.B`, `#class[n]`, `$`, `$form`, `$event`, `$host`, `xfa`), a reference as a value being the node's raw value; assignment to a node (its raw value), to `.rawValue`/`.presence`/`.access`, or to a variable; `var`, `if`/`elseif`/`else`/`endif`, `while`, `for ... upto|downto ... step`, `foreach v in (list, ...) do ... endfor` (the body once per item, a list giving each of its items; `v` holds the node, so `v` reads as its value and `v.rawValue = x` sets it), `break`, `continue`, `func` (hoisted, recursive, `return`); the arithmetic, comparison (`==`/`eq`, `<>`/`ne`, ...) and logical (`and`/`&`, `or`/`|`, `not`) operators with FormCalc's conversions (null and non-numeric text are 0 in arithmetic, a division by zero is null, comparisons give 1 or 0, `null == 0` is 0 but `null == ""` is 1, a node's numeric text compares as a number). A script's value (what a `calculate` writes) is that of the last expression statement evaluated, inside `if` and loop bodies too; one that only assigns keeps what it set.
- **Lists and data** (`script/som.rs`, both languages). `Row[*]` names every node of the name (unnamed subforms transparent), `A..Amount` every `Amount` anywhere under `A` in document order (an index picks among all of them), `A.*` every child, `Row[-1]`/`Row[+1]` the row before or after the one the script runs in (counted from the index of the node of that name at or above the script's node; 0 when there is none). A list member is every item's (`Row[*].Amount` is each row's `Amount`). In FormCalc a list used as a value is its first item's, and the aggregates (Sum, Avg, Count, Max, Min, Concat, NPV) read every item, null items skipped as for any argument (`Count(Row[*].Amount)` counts the filled rows); `Exists` of a list is whether it has an item, `HasValue` and `Ref` read its first; a list as an assignment's target is its first node. `$record` (the data root's first group), `$data` (the data root), `!name` (a child of the `datasets` packet: `!data` is `$data`) and `xfa.datasets` name data nodes: the form keeps the datasets as bound (`Form::datasets`); a data value bound to a field reads the field's current value (so a value a script just set shows), any other the packet's text; data nodes have `value`, `name`, `isNull`, `parent`, `index`, their children by name, and are read, not written.
- **FormCalc built-ins**: Abs, Avg, Ceil, Count, Floor, Max, Min, Mod, Round, Sum, At, Concat, Left, Len, Lower, Ltrim, Replace, Right, Rtrim, Space, Str, Stuff, Substr, Upper, Choose, Exists, HasValue, Oneof, Ref, Within, Null, and (`script/fclib.rs`, `picture`):
  - Dates and times. A date is a day number, 1 being 1900-01-01, over the Gregorian calendar (1900 is not a leap year, 2000 is; 9999-12-31 is the last); a time is a millisecond number, 1 being midnight GMT (so 0 can mean "not a time"). Date (today), Time (now), Date2Num(text [, picture [, locale]]) and Time2Num (the picture read by `picture::parse_value`; without one the text is read leniently, as a fill is; 0 when it does not read), Num2Date(n [, picture [, locale]]), Num2Time, Num2GMTime (formatted by `picture::format`, the locale's medium pattern by default; "" below 1), DateFmt, LocalDateFmt, TimeFmt, LocalTimeFmt (the locale's pattern: 1 short, 2 medium, the default, 3 long, 4 full), IsoDate2Num, IsoTime2Num (canonical text; a zone moves the time to GMT). There are no time-zone data: local time is GMT, so Date and Time follow the system clock in GMT and Num2Time equals Num2GMTime.
  - Format(picture, value) and Parse(picture, text) through `picture` in the script node's locale (its field's, else the form's): a bare picture is tried as a number for a numeric value, else as a date, a time, a date-time and text; Parse gives a number for a numeric reading. "" when nothing formats or reads.
  - WordNum(n [, 0|1|2]) in English (`One Thousand Two Hundred and Thirty-four`, `... Dollars`, `... Dollars And Fifty Cents`; `*` for a negative number or one of a thousand trillion or more). UnitType and UnitValue for `in`, `cm`, `mm`, `pt` and `mp` (a measurement without a unit is in inches; UnitValue converts to inches by default).
  - Apr, CTerm, FV, IPmt, NPV, Pmt, PPmt, PV, Rate, Term with the annuity formulas over `f64` (IPmt and PPmt take an annual rate and walk the monthly schedule, at most 1,000,000 months); a null argument, or one outside the function's domain (a non-positive amount, rate or count where one is needed), gives null.
  - Encode and Decode for `url` (the default: `%XX` for every byte but letters, digits and `-_.~`; `+` decodes as a space), `html` and `xml` (the markup characters as entities; HTML also every non-ASCII character as `&#xH;`; numeric and the common named entities decode).
  - Eval, Get, Post and Put are null.
- **FormCalc script objects**: a `variables/script` object without a JavaScript `contentType` is kept at template read (an empty one is dropped) and its `func`s are called from FormCalc as `Object.Func(args)`, their names resolving from the subform holding the object (so a total over rows names them from there: `T.Row[*].Amount`), and calling each other; statements outside a `func` are not run. A FormCalc script calling a JavaScript script object's function runs it; JavaScript cannot call a FormCalc object's function (it is `undefined`).
- **What does not stop a script**: a construct the reader does not know (regular expressions, `for ... in`, bit operators, object and array literals; in FormCalc anything the reader cannot follow, to the line end, or the whole `if`/`while`/`for`/`func` when its head is the broken part) costs the statement that holds it, not the script; calling a non-function, a missing node from `resolveNode`, or a member a value lacks is `undefined`, never an exception, so the presence lines after a failed validation call still run. A missing `;` at a line end is inserted as JavaScript inserts it.
- **Bounds** (both languages; FormCalc's long string results cost a step a KiB; a list costs a step per item, a reference a step per node its search visited, `foreach` a step per iteration): 4,000,000 evaluations per materialization, 400,000 per script, 20 calls deep, 48 levels of nesting, 1 MiB strings, 4,096 locals per frame, scripts of 256 KiB, 64 events per node, 256 variables per subform. A bound stops that script where it is; what it did stands, the layout proceeds.

The source's /Perms (usage rights, which any change breaks), /Names /JavaScript (the "needs Reader" alerts), /OpenAction and /AA are left out of the materialized document.

Failure falls back: when any step refuses (no template, unreadable XML, an unsupported layout, a limit), the document opens as it did before, placeholder and banner. Materialization never makes an open fail.

## What the renderer does and does not do

Done in this round:

- Template model (`types`): subform, field, draw, exclGroup, area, pageSet, pageArea, contentArea, proto/use, margins, borders (edges, fills, corners), fonts, paragraphs, captions, items, bind, occur, keep, breaks, presence, access, tooltips.
- Binding (`bind`): instances from `occur` and from the data (a repeating subform gets one instance per matching data group), values from the datasets, SOM names with indexes, data paths.
- Layout (`layout`): positioned, tb, lr, table and row layouts; fixed and content-sized boxes (`minH`/`maxH`); an `lr-tb` subform without `w` in a `tb` flow is growable: at least the parent's content width, wider when its line needs it, wrapping only at `maxW` (the bench's item 14, a 5.6 mm check and a 178.2 mm subform behind a 6.9 mm left margin in a 189.9 mm flow, keeps the check beside its sentence as Acrobat does; the root still wraps at its content area); captions by placement and reserve; pagination through content areas and page masters; keep and break; hidden presence; page-master statics.
- Text (`text`, `richtext`): base 14 faces for any family (Arial, Calibri, Myriad Pro and every other sans to Helvetica; serif names to Times; monospace to Courier), metrics from `builtin_metrics` times a per-family width scale (Fonts, below), wrapping (a no-break space ending a word hangs: Designer writes the space after a draw's last word as U+00A0, and Acrobat does not wrap the word for it), alignment, paragraph margins and indents (a negative `textIndent` hangs into `marginLeft` but never starts left of the box: Designer's `textIndent="-14.4pt"` with no margin starts at the box's edge, as Acrobat draws it), rich text runs (bold, italic, underline, size, family, colour, paragraphs, breaks, floating fields).
- Emission (`emit`): pages, content, fonts, the field tree, widgets with /FT, /Ff, /V, /Opt, /TU, /MK-less (XFA draws borders in content), /DA, `TPDFData`, /NeedAppearances true, `/TPDFXfaSig`.
- Sync (`sync`): datasets updated on each fill, and with the values scripts set.
- Scripts (`script`): the JavaScript and FormCalc subsets above, `initialize`/`ready` at open, the filled node's handlers on a fill, with a relayout when they changed what is shown; calculations at open and after every fill; the filled node's validations (result not shown).
- Add and delete rows: push buttons with `click` events get widgets and are listed as `button`; a press runs the click handlers and applies `addInstance`/`removeInstance`/`setInstances` to the datasets, binds again and lays out (above).
- Pictures (`picture`), below: values shown through the field's display picture (`format/picture`) in the widget's /V, in the drawn text of read-only fields and in floating fields; a fill read back through the edit picture (`ui/picture`), the display picture or leniently by value type, the datasets holding the canonical value; `formattedValue` in scripts; the `localeSet` packet's month and day names, symbols and patterns.

Not done (recorded as limits, each a later round):

- **Scripts beyond presence and values.** FormCalc's Eval and URL functions (Get, Post, Put) are null; there are no time-zone data (local time is GMT); SOM predicates (`Row.[Amount > 0]`, `.(...)`) name nothing; data nodes are read, not written (`$record.X.value = 1` does nothing); JavaScript cannot call a FormCalc script object's function, and a FormCalc object's statements outside its `func`s are not run; an unindexed name in another row is its first instance (SOM's index inference from the current instance is not done: `Row.Amount` from inside `Row[2]` is `Row[0].Amount`, a bare `Amount` there is the row's own); a `validate` script's result is not shown and does not reject the value, and calculations stop after two passes; `moveInstance` and `insertInstance` do nothing, `addInstance` returns `undefined` (not the new instance, which exists only after the re-bind), removing the last instance of a subform whose `occur initial` is above 0 brings `initial` blank instances back at the next bind (the data cannot say "none"), a single-stream /XFA (whose datasets are not written) or a form without a datasets packet takes no instance operation, and instance operations of `initialize`, `ready` and `calculate` are dropped; push buttons without `click` events (print, email, submit, reset) get no widget; `xfa.host.messageBox` and the other host calls are silent; regular expressions, arrays and object literals are not evaluated. A handler's effect that the form's `initialize` events do not reproduce from the data is lost at the next fill (the form is rebuilt from the datasets each time), as it is lost at an Acrobat reopen.
- **Pictures, the rest.** A date or time field is a text field in the AcroForm (no date picker; formatting and reading are right). Typed text that no picture or lenient reading takes is kept as typed and stored so (Acrobat would refuse it and keep the old value); a `validate` picture is not checked. Not in the grammar subset: era-relative years and Japanese/Chinese calendars, `datetime` keywords other than date-and-time joined by a space, time zone names (`Z` and `z` show the value's own offset, nothing when it has none), number symbols `8` beyond "a digit, nothing when a trailing zero", `CR`/`DB` beyond their literal forms, locale `zero` digits other than `0`, text symbol `0` as anything but alphanumeric. A date or number field without a display picture shows the canonical value, not the locale's default pattern.
- **Fonts.** Base 14 only, so Arial, Calibri and Myriad Pro render as Helvetica; no embedded fonts, no non-Latin text (WinAnsi, `?` otherwise). Widths are approximated per family (`text::WIDTH_SCALES`): the substitute face's advances times a horizontal scale (Calibri 0.89, Myriad Pro 0.94, Segoe UI 0.95, Verdana 1.12, Tahoma 1.02 against Helvetica; Georgia 1.10, Cambria 1.03 against Times; any other family 1.0), the average advance of ordinary text in the family over the substitute's. The scale is used for wrapping and measuring (captions, values, content-sized boxes) and for drawing: the page content shows those runs under `Tz` (with `Tc` divided by it, as `Tz` scales it too), and a field's /DA carries the same `Tz`, which the forms appearance writer honours (`forms::appearance`: the advances it measures are scaled, the text drawn under that `Tz`). The glyph shapes stay Helvetica's or Times'; a line lands within a few percent of the real font's width, not glyph for glyph.
- **Images, barcodes, signatures** are not drawn (their boxes are).
- **Rotation**, `lr`/`rl` beyond left-to-right wrapping, and `hand` other than inside are approximations.
- **Static XFA** (no `/NeedsRendering`): untouched; its AcroForm pages already render.
- **Reopen after an Acrobat fill.** A file this app materialized and Acrobat later filled shows our widgets' values, not the datasets'.

## Pictures

XFA picture clauses (the XFA 3.3 specification's grammar is the reference; `src/xfa/picture.rs` is a reading of it, in its own words and code):

- **Shape.** A picture is up to 8 alternatives separated by `|`. Each is category clauses — `date{}`, `time{}`, `datetime{}`, `num{}`, `text{}`, `zero{}`, `null{}` — with literal text between them (`date{YYYY-MM-DD} time{HH:MM}`), or one bare body whose category the value type gives (`<date/>` is a date picture). A clause may carry a locale (`num(fr_FR){...}`) and may be a keyword resolved by the locale's patterns: `date.short{}`, `date{long}`, `time.med{}`, `num.currency{}`, `num{percent}`, `num.integer{}`, `num.decimal{}`. A `|` inside one clause (`num{$z,zz9.99|($z,zz9.99)}`, as the locale's currency pattern is written) makes alternatives of that clause. In a body, quoted text is literal (`''` a quote); a run of one character is a symbol when the category has it, literal otherwise.
- **Symbols.** Dates: `D DD` day, `J JJJ` day of year, `M MM MMM MMMM` month, `E EEE EEEE` weekday (number from Sunday, short, long), `e` ISO weekday, `w` week of the month (weeks from Sunday, the first holding the 1st), `WW` ISO week, `YY YYYY`, `G` era. Times: `h hh` (1–12), `k kk` (0–11), `H HH` (0–23), `K KK` (1–24), `M MM`, `S SS`, `FFF`, `A` meridiem, `Z z` the value's zone offset. A `datetime` body splits at an unquoted `T`. Numbers: `9` a digit, `Z` a digit or a space for a leading zero (a trailing one in the fraction), `z` and `8` a digit or nothing, `.`/`V` the locale's decimal, `v` an implied one, `,` grouping (shown after a digit, a space after a `Z` space, nothing before), `$` currency, `%` percent (the value times 100), `( )` around a negative (spaces otherwise), `s` minus or nothing, `S` minus or a space, `-` minus or nothing, `+` minus or plus, `CR`/`DB` (`cr`/`db`) after a negative, `E` an exponent (`E+3`). Text: `X` any character, `A` a letter, `9` a digit, `O` and `0` a letter or digit.
- **Formatting** (canonical to shown). An empty value takes the `null{}` alternative's text (none: empty); a numeric zero the `zero{}` one; else the first alternative that formats. A number rounds half away from zero to the fraction digits; it does not format when its integer part has more digits than the picture or it is negative and the alternative has no sign symbol (the next alternative is tried). A date that is not a real date, a text whose characters do not fit, a malformed picture: the value is shown as it is. Canonical forms read: dates `YYYY-MM-DD` and `YYYYMMDD`, times `HH:MM[:SS[.FFF]]` and `HHMMSS` with `Z` or `±HH[:MM]`, date-times joined by `T`, numbers `[-]digits[.digits]` (an exponent form too).
- **Reading back** (shown or typed to canonical). Each alternative in turn: literals match without case, a space in the picture matches any run of spaces; names match the locale's (case-insensitive); `YY` is 2000–2029 for 00–29, else 1900s; numbers drop the picture's literals, the locale's grouping and currency symbols and spaces, take `( )`, a leading or trailing minus, `CR`/`DB` as negative, the locale's decimal as `.`. Leniently, by value type, when no picture reads the text: dates as canonical, through the locale's four date patterns, three numbers in the locale's short-pattern order (a four-digit first one is a year), or a month name (full, short, or a 3+ letter prefix) with a day and a year, weekday names skipped (`11/05/2026`, `2026-11-05`, `Nov 5, 2026`, `5 November 2026`); times `H:MM[:SS] [AM|PM]`; numbers as above. Text fields have no lenient reading.
- **Locales.** `localeSet` packet → `Locale` (month and day names long and short, meridiem, eras, date and time patterns `full|long|med|short`, number patterns `numeric|currency|percent`, decimal, grouping, percent, minus and currency symbols); what a locale leaves out is `en_US`'s. A field's locale is its `locale` attribute, else its nearest subform's, else the template's (`Form::locale`, `en_US` when unset); a missing locale falls back to one of the same language, then `en_US` (from the packet when it has one, else built in).
- **Where it runs.** `picture::shown` gives the text of a field with a display picture: its widget's /V (`emit`), its drawn value when read-only (`layout`), its text inside rich text when it is a floating field (`bind::record_ids`), and `formattedValue` in scripts (assigning it reads it back). The datasets, `rawValue`, calculations and the signature keep the canonical value. On a fill, `sync_datasets` writes the typed text as before; `xfa::build` (`canonicalize_fill`) then reads it with the field's edit picture, its display picture, or leniently, sets the canonical value on every fillable field bound to that data node (the datasets take it through the usual changed-values update, in the same journaled step), and lays out again when the field now shows something other than what was typed, so the widget shows the formatted value. A numeric field without a picture stores its typed number canonical (`$1,234.50` → `1234.50`). A date or time field stays a text widget.

## Module contracts

The signatures in `src/xfa/*.rs` are the contract between the four implementers; `types.rs` is the shared model. In brief:

- `xml::parse(&str) -> Result<Element, XmlError>`, `xml::serialize(&Element) -> String`; `Element` keeps qualified names, `local()` strips prefixes.
- `packets::read(&Document) -> Result<Packets, XfaError>`, `packets::is_dynamic(&Document) -> bool`.
- `template::read(&str) -> Result<Form, XfaError>`: one instance of each subform, protos resolved.
- `bind::bind(&mut Form, Option<&Element>) -> Result<(), XfaError>`: instances, SOM names, data paths, values.
- `text::block`, `text::lay_out(&Block, Option<Pt>) -> LaidBlock`, `text::face_for`, `text::advance`, `text::win_ansi_code`; `richtext::parse`, `richtext::plain_text`.
- `layout::lay_out(&Form) -> Result<Vec<Page>, XfaError>`: paint-ordered items in page points, y-down.

Coordinates: XFA and the layout are y-down in points from the page's top-left; PDF content is y-up, so the emitter maps `y_pdf = height - y - h`. The forms module's page space is also y-down (`forms::PageSpace`), so widget rects pass through `to_pdf`.

Field names: the SOM name with indexes (`form1[0].StatusCertificate[0].Section1[0].CCName[0]`), as Acrobat names an XFA-backed AcroForm's fields, one /T per step. Depth stays under `forms::MAX_FIELD_DEPTH` for real forms; a deeper path is flattened at the top (the first steps joined into one /T with the dots replaced by `_`).

Check buttons: the on state's name is the on item's save value (`/1`), so /V and /AS carry what the datasets store. Radio buttons: one AcroForm radio field per `exclGroup`, kids named by their on values. Choice lists: /Opt as `[export display]` pairs.

## Limits

`xfa::limits`: 64 MiB of packets, 2,000,000 XML elements, 512 levels, 200,000 form nodes after expansion, 2,000 pages, 1,000,000 items, 1 MiB of characters per text block, 1,024 instances of one repeating subform through `instanceManager` (its `occur` max when lower), 1,024 instance operations per materialization (a `setInstances(1e9)` stops there; the re-bind still counts every node against the form-node limit). Pictures (`picture`): 256 characters, 8 alternatives, values and typed text of 512 characters, 64 locales from the packet; a picture past them, or malformed, is not used (the value shows as it is). Every reader and the layout stop at them with `XfaError::Limit`, never a panic; hostile templates (cycles in `use`, unbounded `occur` with data, a content area of zero height) are tests. Scripts have their own bounds (above); a runaway script (`while (true)`, unbounded recursion, a string doubled forty times) is a test too.
