## Truncated incremental update (open, major): decided, last complete revision

- Decision: objects appended after the last `%%EOF` without their xref section are in no revision. The repair's xref read (`read_xref`) takes the last `startxref` in the final 1,024 bytes, MuPDF's `pdf_read_start_xref` window, and selects the objects its chain names whatever follows; the file is rebuilt from that revision, `repaired: false`, versions as its sections count. Past the window no `startxref` is found and, as in MuPDF, the file is scanned and the appended objects win (`repaired: true`).
- Why: a reader that shows bytes no xref names shows a state no writer committed (an interrupted save) or content appended to a signed file outside any update; MuPDF shows the last complete revision. On `fixtures/p0b/signed-intact.pdf` with a replacement content object appended, the app now shows the signed text and `sign-list` counts 2 versions, as engine.ts does (before: the appended text, 1 version). The verifier's coverage report is unchanged (the bytes after the signed revision are still not covered).
- Before, any object, trailer or xref stream after the last `startxref` made the repair ignore the xref and scan. Changed existing tests (added during this rewrite, encoding the old policy): `tests/repair.rs` `incremental_update_with_broken_xref_keeps_the_newer_objects` now expects the last complete revision for an update whose section or trailer was cut off ("cut trailer", "no section"); an update whose own section is damaged (its `startxref` names it) still keeps the newer objects. `generic_damage_to_fixtures_is_repaired` expects the earlier revision, unrepaired, when a fixture with several revisions is cut at its last xref and the earlier `startxref` lies in the window (`p0b/certified-p2-annot.pdf`).
- Tests: `tests/app_corpus_open.rs` `objects_appended_without_an_xref_leave_the_last_complete_revision` (an existing and a new object number; past the window), `a_signed_file_with_an_appended_object_shows_the_signed_revision`.

## A dictionary that lost its `>>` hides the next object (open, blocker): fixed

- Verified: round 2's dictionary reparse read a dictionary missing its `>>` (`/Foo 1`, `/Foo (abc)`, `/Foo 9 0 R`, with or without `endobj`) to the end of the input; it failed on the next header's number, and the resume rule then skipped that header. With an intact xref, `select_by_xref` met an entry at a header it had neither defined nor recorded as failed and gave up the whole xref; with a broken one the object was simply gone.
- `select_by_xref` now reads any in-use entry the scan did not define at its own offset (`header_at`: `N G obj` exactly there, its number the entry's; `read_at`, accepted when `endobj` or `stream` follows), as MuPDF reads an object at its xref offset. One that does not parse is left out as null (`objects_unreadable`, `repaired: true`) and the rest of the xref kept; an entry that points at no header of its number still means the xref is broken and the file is scanned.
- The scan no longer reads a dictionary past a header that starts a line and whose own object parses through `endobj` (or a dictionary to `stream`; `Scan::whole_object_at`, the object read alone up to the next event). For a header in mid-line it still rereads (a header inside a value, `/A 3 0 obj`, round 2); when that reread fails on the header's own number, the header is skipped only if its object does not parse whole, so `/Foo (abc)4 0 obj` keeps object 4.

## Review of round 3: two minors, fixed

The re-review accepted `open` and found two minors in the loose-dictionary change above.

- **Loose dictionaries overrode an intact xref.** A 2-page plain file with `<< /Encrypt <<...>> /ID [...] >>` between objects (offsets valid) or after `%%EOF` opened locked with no password working. `<< /Info 7 0 R >>` after `%%EOF` put the wrong title in the save; MuPDF and round 2 read both normally. Now, when the xref chain describes the objects (`select_xref`), the trailer entries are the chain's, as the strict reader takes them (`chain_entries`, `Document::trailer_entry`): /Root from the newest trailer that has one, /Info, /ID and /Encrypt from the newest trailer only. The scan's harvest (trailer keywords anywhere, dictionaries outside objects) is used only when the file is scanned. `finish` first reads the chain, chooses the handler with its entries and selects by the xref; if the xref does not hold, it restores the harvest, chooses the handler again and selects from the scan. Side effect: a complete `trailer` after the chain (after `%%EOF`) no longer overrides it either, as in MuPDF (round 2 took its /Info). Test: `loose_dictionaries_do_not_override_an_intact_xref` (/Encrypt with /ID, /Info and /Root, between objects and after `%%EOF`; a whole `trailer` after `%%EOF`).
- **Junk between objects used up the rereads' budget.** Failed loose-dictionary parses were charged to `wasted`, which `reparse` checks, so 2 KB of `<< /A (xxx...` in a 3.2 KB file with a broken xref left a page whose string holds `\n12 0 obj\n` blank in the view and the save. They now have a one-pass budget of their own (`loose_wasted`); work stays linear (the scan's rereads, the xref's rereads and the loose dictionaries, one pass each, plus successes). Test: `junk_between_objects_does_not_starve_rereads`.
- Both tests fail before the fix. Reruns on the fixed build: the reviewer's `r5-loosejunk` (every row reads as MuPDF: 2 pages, the right title, unlocked) and `r4-budget` (every broken-xref row keeps all three texts; loose-junk timings at most 21 ms for 256 KB); cut fuzz seeds 1-3 and the paired robustness fuzz (9,600 inputs) give exactly the counts of the run above; `q8` and `q12` unchanged; the 300 corpus files any run repaired or refused (`p8-open-final-sub3`) are identical to the previous final run.
