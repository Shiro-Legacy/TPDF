## Lexical damage the repair reads through (open, blocker): fixed

- Verified: one damaged token in an object the strict reader refuses made the repair drop the whole object (a blank page, an annotation or form gone, a catalog refused, an R6 /Encrypt dropped so the file opened with no pages), and the save wrote the loss.
- MuPDF 1.28.1's reading, measured on a page dictionary (`/X tok /Y [1 tok 3]`), is now the repair's (`Lexer::with_lenient`, `Parser::with_lenient`; the strict reader is unchanged):
  - Number tokens (first byte `+ - .` or a digit): extra `-` after a leading `-` are skipped; a second `.` or any byte other than a digit, `.` or `-` makes the token a keyword, read as null (`1e5`, `1.0E-4`, `1.2.3`, `1..5`, `12abc`, `0x10`, `1,5`, `7g2`, `-+5`). Otherwise the value is read after its signs up to its first other byte: `--5` -5, `5-` 5, `-5-` -5, `+-5` 0, `-`, `+`, `.` 0, `1.5-3` 1.5, `1-.5` 1. Integers past i64 wrap (`18446744073709551617` is 1); such a real's integer part wraps past u32 (`4294967296.5-` is 0.5).
  - Keywords: any regular byte (`\xA5`, `true1`, `nul`, `NaN`, `bogus`); a stray `)`, `>`, `{` or `}` is a one-byte keyword. Inside an array or dictionary every keyword but `true`, `false`, `null` is null, `obj`, `endobj`, `stream`, `xref`, `R` included (MuPDF: the same in a dictionary), and so are a stray `]` as a dictionary value and `>>` in an array (`/MediaB792]`, a cut the review's fuzz made: MuPDF reads `/MediaB792 null` and keeps the page).
  - Hex strings: a non-hex byte is the digit 0 (`<ABQD>` is `<AB0D>`, `<A B Q>` `<AB00>`).
  - A dictionary value starting with an integer is that integer before a name or `>>`, a reference for `N G R`, and otherwise null, consuming the next token (and after a second integer the one after it): `/A 1 bogus /B 3` and `/X 4 0\xA5R` give null and keep the rest. A reference to object 0 or past u32/u16 is null.
  - Still refused, as by MuPDF: a key that is not a name (`/A 1 2 /B 3`, where MuPDF too consumes `/B`; `/A (x) (y)`), an unterminated hex string, and a whole object whose value is an unknown keyword. More lenient than MuPDF: `[R]` and `[1 R]` read as null entries where MuPDF fails the object.
- The reviewer's suggested rule (a number's longest valid prefix: `1.0E-4` as 1.0, `1.2.3` as 1.2) is not MuPDF's: MuPDF reads those as null. The measured rule was implemented.
- Such a file is still refused by the strict reader, so it is rebuilt from its own xref; when the xref is intact it is shown `repaired: false`, as MuPDF shows it (before: `repaired: true` and the object dropped). Typing a catalog whose /Type is missing or null (`/Type \x98Catalog`) no longer counts as damage either: MuPDF reads such a catalog as it is.
- Not done, rejected: "fall back to a /Pages scan when the catalog fails, as MuPDF's `pdf_repair_trailer` does". Measured: MuPDF opens no pages for a file whose catalog is missing or does not parse (engine.ts "open: PDF has no pages"; Rust "open: the file could not be read (PDF repair: invalid document catalog)"); both refuse. A catalog with a damaged value (`/Type \x98Catalog`, `/X 1e5`) now parses, which was the case the finding measured.
- Gap left to the view: a non-hex byte in a hex string inside a content stream (`<5044Q641> Tj`): MuPDF draws the string with a 0 digit; hayro's content lexer drops it. Content streams are the view's (an upstream hayro change); the save keeps the bytes, which MuPDF reads alike.
- Observed in the fuzz, not changed (not lexical, recorded here): an encrypted file whose catalog no longer parses opens locked in MuPDF, which reads no catalog before the password, and has 0 pages after it (4 of 4 checked); the app refuses it at open ("could not be read"). A page whose /Type is damaged into another name (`/Type /endstreamPage`): MuPDF counts every kid whose /Type is not /Pages as a page; the app's page walk (hayro's, `info::pages`) does not, so a one-page file has no pages ("PDF has no pages"). Page classification belongs with the walk the core and view share (`app-corpus-open.md`, saved page trees).
- Tests: `tests/lexer.rs` `lenient_numbers_read_as_mupdf_reads_them`, `lenient_hex_strings_keywords_and_stray_delimiters`; `tests/parser.rs` `lenient_values_read_as_mupdf_reads_them`; `tests/app_corpus_open.rs` `a_damaged_token_in_a_page_dictionary_keeps_the_page`, `a_damaged_token_keeps_annotations_forms_and_the_catalog`, `a_damaged_matrix_entry_keeps_the_form`, `a_catalog_with_a_damaged_type_opens`, `a_non_hex_character_in_the_encryption_dictionary_reads_as_zero`, `a_stray_closing_bracket_in_a_page_dictionary_keeps_the_page` (20 tokens each in a page, an annotation, a form XObject and the catalog; each save is validated and reopened with its text). ## Truncated incremental update (open, major): decided, last complete revision

- Decision: objects appended after the last `%%EOF` without their xref section are in no revision. The repair's xref read (`read_xref`) takes the last `startxref` in the final 1,024 bytes, MuPDF's `pdf_read_start_xref` window, and selects the objects its chain names whatever follows; the file is rebuilt from that revision, `repaired: false`, versions as its sections count. Past the window no `startxref` is found and, as in MuPDF, the file is scanned and the appended objects win (`repaired: true`).
- Why: a reader that shows bytes no xref names shows a state no writer committed (an interrupted save) or content appended to a signed file outside any update; MuPDF shows the last complete revision. On `fixtures/p0b/signed-intact.pdf` with a replacement content object appended, the app now shows the signed text and `sign-list` counts 2 versions, as engine.ts does (before: the appended text, 1 version). The verifier's coverage report is unchanged (the bytes after the signed revision are still not covered).
- Before, any object, trailer or xref stream after the last `startxref` made the repair ignore the xref and scan. Changed existing tests (added during this rewrite, encoding the old policy): `tests/repair.rs` `incremental_update_with_broken_xref_keeps_the_newer_objects` now expects the last complete revision for an update whose section or trailer was cut off ("cut trailer", "no section"); an update whose own section is damaged (its `startxref` names it) still keeps the newer objects. `generic_damage_to_fixtures_is_repaired` expects the earlier revision, unrepaired, when a fixture with several revisions is cut at its last xref and the earlier `startxref` lies in the window (`p0b/certified-p2-annot.pdf`).
- Tests: `tests/app_corpus_open.rs` `objects_appended_without_an_xref_leave_the_last_complete_revision` (an existing and a new object number; past the window), `a_signed_file_with_an_appended_object_shows_the_signed_revision`.
