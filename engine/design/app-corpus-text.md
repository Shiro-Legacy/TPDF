# Corpus: text extraction (render text, text-all, search)

October 16, 2026. The text classes of the corpus differential (`reference/corpus-20261015/README.md`: `text-differs`, `textall-differs`, `search-differs`, `text-space-differs`), fixed in `src/view/stext.rs` and the new `src/view/text_unicode.rs`. Read with `../APP-ENGINE-DESIGN.md` (View ops) and `app-view.md`. Every rule below was measured with MuPDF 1.28.1 (the app's `node_modules` copy) on synthetic pages; `tests/view_text.rs` holds those pages and MuPDF's text for them.

## Character codes to Unicode (`text_unicode.rs`)

- `FontText` gives each code of a font the text MuPDF derives (pdf-font.c, pdf-type3.c, pdf-unicode.c); a code it does not settle keeps hayro's reading. The scan queues every show operation hayro will draw (codes split as hayro splits them, string by string, under the font's key; Type3 shows in one queue, hayro not saying which Type3 font drew a glyph). A glyph run takes a queued show only where it lands: as many glyphs, the same linear part of the first glyph's transform, and its translation where the scan knows the pen (after `BT`, `Td`, `TD`, `T*`, `Tm`, `'` or `"`); after another show of the text object, only when the run just before took that show; anywhere for a vertical font (its glyphs are displaced by metrics the scan does not read). Runs come in content order, so shows queued before the last one taken are dropped; a run no show fits keeps hayro's reading. The scan mirrors what hayro draws: forms with a /BBox only, `Tr` by its last operand, `Tj` and `TJ` without a font in Helvetica (ASCII strings only, also for a `Tf` naming a font the resources lack), `'` and `"` without a font not at all. (Matching by font and glyph count alone gave a run the text of a show hayro had not drawn: a form without /BBox, `1 7 Tr`, mode 7 inherited by a form.)
  - **ToUnicode**: hayro's parse, else the mapping blocks alone (`mapping_blocks`): MuPDF skips any other token, such as a name cut short by a stray `>` or a CMap name with spaces, and fails the CMap only on a malformed block. A ToUnicode CID mapping (`begincidrange`) gives the CID as the character. White-space controls read as a space, other controls as no mapping; a stream that does not parse gives no text and no fallback.
  - **Composite fonts** without ToUnicode: the collection's UCS2 CMap; a non-embedded Identity font MuPDF's TrueType-UCS2 (the Macintosh glyph order).
  - **Simple fonts**: the encoding's glyph names; else the font's built-in encoding: MuPDF's Symbol, ZapfDingbats or Standard faces when not embedded, a TrueType program's cmap (MuPDF's `select_truetype_cmap`) and `post` names (WinAnsi names without them). An embedded Type1 or CFF program's built-in encoding keeps hayro's reading.
  - **Type3**: the encoding's glyph names (Standard without an encoding), a printable ASCII code without a known name as itself.
  - **Glyph names**: MuPDF's glyph list (4,441 names, measured through Type3 fonts by `tools/probe-text-unicode.mjs` into `reference/text-unicode-20261015/mupdf-unicode.json`, generated into `text_unicode_data.rs` by `tools/generate-text-unicode.py`), the TeX ligatures, `uniXXXX`, `uX…` and `aNN` read whole as C's `strtol` reads them.
  - **S22PDF's Chinese fonts** (a WinAnsi font of Flags 4 whose BaseFont is one of five GBK-encoded face names): GBK-EUC-H codes through Adobe-GB1-UCS2, every code an em wide (MuPDF loads them without their /Widths). pdf.js `SimFang-variant.pdf` and `XiaoBiaoSong.pdf` are such fonts, not TrueType fonts MuPDF maps through a cmap.
  - Presentation forms and ligatures split as MuPDF's structured text splits them (measured table, 788 forms); a control character from hayro's own reading is a space (white-space controls) or U+FFFD.
- A `TextReader` keeps each font's `FontText` with its fonts (cleared when the reader starts afresh), so search and text-all build it once per document rather than once per page, and shares the predefined CMaps they use by name (each font kept its own: a page of 200 Japan1 fonts without programs peaked at 441 MB, 224 MB now, 222 MB before the work). The font program is decoded once per page per font, for its facts and its text.
- TrueType cmaps: the 512 codes a simple font may read (and 0xF000 plus each) are looked up in one pass over a format 4 subtable's segments (the first segment ending at or after a code decides it, as before) and by bisection in a format 12 or 13 subtable's groups (sorted, as FreeType requires). Walking every group for each code made eight fonts sharing a program of 500,000 groups take seconds.
- WASM: 11,896,744 → 12,097,819 bytes (+201,075: the glyph list, forms and bidi tables and the code) → 12,120,598 with the review fixes (show placement, the Type3 budget, shared CMaps).

## Layout (`stext.rs`)

- **Clipping text** (Tr 7). hayro draws nothing for mode 7, so the page's own content is interpreted with `4 Tr` after every `Tr` hayro reads as 7 (`clip_mode_content`: hayro's parser finds the operators and reads the last operand; the copy is made only when the page shows text in mode 7); the scan knows which shows were mode 7, including in forms drawn with the page's mode 7, and the device drops their fill. MuPDF extracts a text object's clipping text again at its ET, as a new object, each glyph's first character only (no one-to-many fillers), when the object's last show was in a clipping or the invisible mode, and drops it otherwise or without ET; a text object never ended goes on at the next BT. Rust does the same for the mode 7 glyphs; the clip text is emitted at the next device call after the object (the clip hayro pushes at ET, or anything drawn).
- **Clip test**. A glyph is dropped when its bounds lie wholly outside the clip; an inkless glyph's bounds are its origin (MuPDF's `fz_glyph_entirely_outside_box` with an empty glyph box). The previous rule dropped every inkless glyph of a run with ink outside the clip, so spaces vanished from text in a narrow clip.
- **Directions**. MuPDF reads R and AL right to left, L, EN, ES and ET left to right, and lets AN, CS, NSM, BN, B, S, WS and ON take the direction of the character before; a text object starts left to right. A change of direction starts a span (a line of the render text). The classes come from Python's `unicodedata` (Unicode 16, 676 ranges); hayro's and the old ranges missed the right-to-left scripts past the BMP and every neutral character.
- **Spans**. MuPDF flushes its text, so the next show starts a span, at q, Q, cm, w, J, j, M, d, ri, gs, every colour operator (even setting the same colour), MP and DP; not at Tf, Tr, Tm, Tc, Tw, Tz, Ts, i, BX or path construction. Text in another rendering mode is another span.
- **ActualText over no text** sits on the images and shadings the span drew (an image's bounds from its pixel grid; the old code used one pixel), nothing over paths alone; its characters after the first follow the first as one glyph's would, so repeated letters do not read as fake bold (the old placement read pdf.js `issue9972-1.pdf`'s figure text with one letter of each double).
- **Type3 glyphs drawn directly** (each its own span): the check follows the forms a glyph procedure draws, with the state at their `Do`, at most 16 forms per glyph; `d1` counts whatever its operands. It runs for the codes a page shows, once per glyph procedure (by object and font resources) for a reader, and a page may read 4 MiB of decoded procedures and forms for it: each procedure costs the page its bytes once, whether an earlier page read it or not, so a page reads the same with or without the reader's memory; past the budget, glyphs read as cached. (Checking every code of every Type3 font a page set, each name decoding its procedure again, took 72 s for 20 pages of a font whose 256 names share one 2 MB procedure, 0.4 s now.)
- **Fonts**. A form draws with the text state of the content that draws it (the scan started forms afresh). Text is what hayro draws, so the page's render and its text agree: without a font, `Tj` and `TJ` show ASCII strings in Helvetica.
- **Structure ActualText**: the MCIDs a page's content marks are looked up after the content, in one pass over its /StructParents array, which stops after the last MCID used and keeps only the items asked for. Looking each MCID up with `iter().nth(mcid)` resolved every element before it: 6,000 MCIDs took 8.7 s natively; the test's page of 6,000 takes 7.8 s at the parent commit and 0.02 s now.
- Optional content as hayro evaluates it, so a show hayro skips is not queued; ActualText ends at its first NUL (MuPDF keeps it as a C string).

## Differences from MuPDF and engine.ts

- Text in clipping modes 4 to 6 reads once: MuPDF extracts it as drawn and again as the clip at ET, so a filled clipping word was found twice by search and repeated by copy. Only mode 7 text, drawn in no other way, is extracted at ET (`7 Tr (AB) Tj 4 Tr (CD) Tj` reads "CD", then "AB"; MuPDF "CD", then "BCD").
- Text shown before any `Tf` with `Tj` or `TJ` is extracted, in Helvetica, as hayro draws it on the page (MuPDF draws and extracts nothing); `'` and `"` without a font show nothing in either. The view draws what Acrobat draws; text and render agree.
- A form without a /BBox is not drawn by hayro, so neither its render nor its text appears (MuPDF draws it). `Tr` with extra operands takes the last as hayro does (MuPDF the first): `1 7 Tr` is clipping text in Rust, stroked in MuPDF. `Ts` follows hayro's operand rule too: extra operands give the last (`5 30 Ts` raises 30; MuPDF 5), and a name or missing operand keeps the previous rise (MuPDF: 0). The edit scan reads `Ts` as MuPDF does (`app-edit.md`).
- Clipping text in a form's content (mode 7) is not extracted: hayro draws forms from the document, so their content cannot be rewritten. No corpus file has it (6 have mode 7 text, all in page content).
- Text inside Type3 glyph procedures and inside tiling pattern cells is not extracted; MuPDF extracts it when it draws the glyph or cell directly (pdf.js `ContentStream*Type3insideType3.pdf`, `issue15716.pdf`).
- MuPDF takes a structure element's ActualText from the first element of the /StructParents array whose /K names the MCID (an integer or an array of them, not a marked-content reference); the engine takes the element at the MCID, as the specification does. They agree on well-formed files.
- ActualText characters beyond the glyphs they replace stay on the glyphs' line (the existing decision, APP-ENGINE-DESIGN.md); MuPDF starts a span for them (veraPDF 6-2-11-7-3 ×6, 6-2-10-8 ×2: same text, other line breaks).
- hayro's CMap data: Adobe-GB1-UCS2 reads GBK's ellipsis as U+2026 and its half-width space as U+2002 where MuPDF's has U+22EF and U+0020 (XiaoBiaoSong).
- Glyph names MuPDF's list lacks but hayro reads (TeX's `integraldisplay` as ∫) keep hayro's reading in embedded Type1 and CFF fonts; MuPDF gives U+FFFD (veraPDF 6-3-8 and 6-2-11-7-2).
- Not fixed, in hayro (patches are for panics only): a hex string with a non-hex character drops the show (MuPDF skips the character; veraPDF string objects ×3); a CMap stream's /UseCMap in its dictionary is not followed (veraPDF A025 ×2); a CMap whose dictionary /WMode disagrees with its program uses the program's (MuPDF the dictionary's; veraPDF and Isartor CMaps t02 ×9).
- **Gaps of 0.15 em** (the space threshold): MuPDF reads a gap of exactly the threshold on either side of it, by the single-precision rounding of its own coordinates (synthetic Helvetica pages: `[(a) -150 (b)] TJ` reads "a b" at 10 points and `[(a) -150 (b) -150 (c)] TJ` "abc" at 12; letter spacing of 0.15 em "a b c" at 10 points and "abc" at 12). Within 1e-5 em of it, the engine reads a gap made by a `TJ` adjustment below it (TeX's ellipsis kerns: 17 pdf.js tracemonkey files) and one made by positioning or letter spacing above it (govdocs1 `000348.pdf`'s leader dots before page numbers, `000153.pdf`'s letter spacing), as those corpus files read in MuPDF, whichever side of 0.15 hayro's coordinates put the gap. The first version of this work read every such gap below: `000348.pdf` lost 18 spaces it had at the parent commit. Emulating MuPDF's single-precision arithmetic from hayro's coordinates matched neither.
- MuPDF loses text in malformed content where hayro keeps it (qpdf `compare/start.pdf`, `split-content-stream-errors.pdf`, `stream-line-enders.pdf`, pdf.js `operator-in-TJ-array.pdf`), and drops a page's later text after a form leaves a pending `W` (pdf.js `issue6413.pdf`); and hayro reads the Japanese 90ms-RKSJ-H sample MuPDF shows as U+FFFD. Rust keeps its text.
- Search keeps the recorded differences (APP-ENGINE-DESIGN.md): one hit per match where MuPDF counts a match across a line break (a soft hyphen) as one hit per quad (govdocs1 `000314.pdf`, `000571.pdf`), and no per-page limit of 500 quads (veraPDF implementation limits ×3).

## Tests

- `tests/view_text.rs` (synthetic pages, MuPDF's text for each): clipping text, clip bounds, directions, span starts, ActualText over images, Type3 glyphs drawing forms, lenient ToUnicode, S22PDF fonts, text before a font, and the MCID lookup's time (under 3 s for 6,000 MCIDs).
