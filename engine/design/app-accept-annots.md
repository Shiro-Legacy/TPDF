# Acceptance review: annots, annot-add, annot-set, annot-move, annot-delete (round 1)

October 16, 2026. Fixes for the acceptance review of these ops at ed62a16 (verdicts: annots, annot-move, annot-delete accepted; annot-add and annot-set not accepted). Read with `../APP-ENGINE-DESIGN.md` and `app-annots.md` (corrected where these fixes change it).

## Shared /Annots (blocker, annot-add; link-add too)

- **Verified.** Pages sharing one /Annots object: annot-add appended to the shared array, so the new annotation (and a note's popup) showed on every page listing it, in the view and the save. mupdf.js 1.28.1 through engine.ts, measured again: `createAnnotation` and `createLink` leave the page a direct array (the shared object unchanged, the other pages listing nothing new); field-add already writes a direct array (engine.ts `directAnnots`, `ops/fields.rs` `direct_annots`).
- **Fix.** `annots::own_annots(target, page)`: when the page's /Annots is an array object another page lists too (another page object, or a page written into /Kids; one page object the tree lists twice is one page), the page gets a direct copy of it in the same step. `annots::append` runs it before every append, so annot-add (annotation and popup), redact-add and redact-search (`redact::marks::write_plans`, whose own copy it replaces) get it; link-add (`ops/nav/links.rs` `add`) calls it before its own append. An unshared array object is still edited in place (MuPDF makes it direct too; both draw and save the same).
- **Change for redaction** (`app-redact.md` updated): a page written directly into /Kids now gets its copy in its dictionary there; it kept the shared array before.
- Removal still edits the shared array (MuPDF's `deleteAnnotation` does; the review measured saved results equal).
- Test: `an_add_on_a_page_sharing_its_annots_array_lands_on_that_page_alone` (`tests/app_annots.rs`): three page objects and one page in /Kids share `5 0 R`; a Square and a note on page 0, a Circle on the /Kids page, a link on page 1; each page lists only its own, the shared array is unchanged, the reopened save agrees, four undos restore every object exactly. The redact test `a_mark_lands_only_on_its_page_when_pages_share_an_annots_array` passes unchanged.

## FreeText text outside WinAnsi (blocker, annot-add and annot-set; minor, annot-move)

- **Verified.** `appearance::layout` encoded every FreeText with `fonts::encode` (WinAnsi, `?` otherwise): the text-box tool (annot-add without `fit`), comments-panel edits (annot-set regenerates every FreeText), the move of a FreeText without an appearance and the view's synthesis of one drew Greek, Cyrillic, CJK and Latin Extended as `?` and saved them so. The design note recorded the rule without a reason; there is none.
- **MuPDF measured** (mupdf.js 1.28.1, FreeText `update()`): `write_variable_text`, the same layout as widgets: one run per font, `<DA>GRK` (ISO 8859-7) and `<DA>CYR` (KOI8-U) re-encoded base 14 fonts, `Song`/`Mincho`/`Batang`/`Ming` UTF-16 CID fonts (Han by /Lang), Common characters in the font of the run they are in (or of the first scripted character), a trailing line feed and an empty text draw no line, a centred or right-aligned line leaves the break's trailing space out of its width. Latin letters WinAnsi lacks (Polish, Czech, ...) and Vietnamese: the whole text in an embedded Nimbus Sans program (Identity-H), Vietnamese letters it lacks as .notdef; emoji as .notdef.
- **Fix.** `appearance::free_text_lines` lays the text out through the forms group's `scripts::lines` (CRLF normalized to one break, the recorded difference), with the DA font's own WinAnsi advances (`forms::text::Metrics::from_widths` from `annots::fonts::Base14`, so WinAnsi layout keeps its widths); `free_text` writes each run as MuPDF does (`/<font> <size> Tf`, a raw literal or UTF-16 hex) and names the fonts under MuPDF's resource names. Han takes the annotation's /Lang, else the catalog's (`pdf_annot_language`). `annots::put_appearance` stores a CJK font as three objects (descriptor, CIDFont, Type0) since a font descriptor is an indirect reference; the view's synthesized forms keep them direct (view only).
- **Latin letters: a deliberate difference.** The engine has no font program to embed, so Latin letters WinAnsi lacks take a re-encoded base 14 font `<DA>LAT` (`scripts::Eight::Latin`, `LATIN_EXTENDED`): Latin Extended-A but the seven WinAnsi has, and S and T with comma below, 125 glyphs named by their Adobe glyph names, widths from URW's metrics (all 125 in Helvetica, Helvetica-Bold, Times-Roman and Bold Oblique). It is MuPDF's own Greek and Cyrillic scheme: viewers draw the glyph names from their base 14 font (MuPDF's Nimbus Sans and the view's URW outlines have all of them; a viewer whose base 14 font lacks one draws its own fallback). MuPDF lays such a text out with the program's metrics and its first baseline 0.9 size below the box top (0.8 otherwise); a text with a Latin-font or `?` character takes that baseline here too (measured: MuPDF draws both saves of Polish, Czech and Romanian boxes pixel-identical, and accented capitals of the first line are not clipped). The text stays extractable (glyph names) and the file small (four such boxes: MuPDF's save 46,814 bytes, the app's 7,797). Widgets keep MuPDF's fonts (`Fonts::latin_extended` false): their lossy rule (no /AP, NeedAppearances) is the forms group's.
- **Still `?`:** characters none of these fonts has (Vietnamese letters outside Latin Extended-A, emoji, other scripts); MuPDF draws .notdef (nothing) for most of them, keeping the characters only in its ToUnicode. Recorded: a visible `?` says a character is missing where MuPDF leaves a gap; /Contents keeps the text either way. Text past 65,536 characters (`MAX_FREE_TEXT_CHARS`; the app writes at most 4,096 UTF-16 units) and lines below the box are not laid out.
- **Behaviour change in WinAnsi text** (MuPDF's): a centred or right-aligned wrapped line is placed by its width without the trailing space (measured: Q 1, `2 -14.4 Td` where the old layout wrote 0.332), and a trailing line feed or an empty text no longer writes a `Td` for an empty last line. Nothing drawn changes otherwise; `free_text_lines_break_as_mupdf_breaks_them` (unit test added during this rewrite) now expects no line for an empty text, as MuPDF (it expected one empty line).
- `fit` keeps engine.ts's WinAnsi check (`unsupported-encoding`), as before.
- Tests: unit `free_text_runs_take_mupdfs_fallback_fonts` (MuPDF's runs for `abc Ωmega Жук 中文 end`, Common characters ahead of a script, the centred width, Latin and `?` runs), `free_text_lines_break_as_mupdf_breaks_them` (trailing break, CRLF, the line limit and the character cap); native `free_text_draws_greek_cyrillic_cjk_and_latin_letters_in_fallback_fonts` (resources and runs of an added box, the Song font as three objects, the /Differences, each of Ω μ Ж ż ł ő ș drawn by the view from the reopened save and not as `?`; annot-set of a foreign FreeText to Cyrillic; annot-move of an appearance-less Greek FreeText).

## Icon stamp fit (major, annot-add; minors, annots and annot-set)

- **Verified.** `appearance::icon_fit` kept the rect's width and set the height to 50/190 of it, so a rect wider than 190:50 (a search hit padded 4 pt) gave a stamp taller than the rect, past the page top. MuPDF fits the 190 x 50 box inside: scale min(w/190, h/50), centred (measured: [10 10 410 60] → [115 10 305 60], [10 10 600 100] → [134 10 476 100], a foreign /Rect [300 600 500 650] without /AP → [305 600 495 650]). The design note's "keeping the width, as MuPDF" held only for narrower rects.
- **Fix.** `icon_fit` fits inside; annot-add, the view's synthesis (`view::rect_box`), the `annots` listing and annot-set of a stamp without an appearance all use it. Narrower rects are unchanged.
- Tests: unit `an_icon_stamp_fits_inside_its_rect`; native `an_icon_stamp_fits_inside_a_rect_wider_than_its_icon` (both rects, listed and saved; the foreign stamp listed and after annot-set). The existing `annotations_without_an_appearance_list_and_save_the_rect_mupdf_derives` (a square rect) passes unchanged.

## Stamp images shared (major, annot-add)

- **Verified** by the review's p14 (the same 3.76 MB JPEG on 16 pages: Rust refused the save at the 50 MiB ceiling, engine.ts saved 3.8 MB): every stamp stored its own copy; the design note recorded that without its consequence.
- **Fix.** `images::store_shared`: before storing, the image is compared with each image a Stamp's normal appearance shows as /I on any page (`ops/annots.rs` `stamp_images`); one holding exactly what `store` would write (samples, dictionary but /Length, soft mask and ICC profile streams) is reused and nothing is written. Samples are compared only when their lengths agree. Nothing is kept outside the document, so undo, redo and other ops cannot leave a stale entry: an image no listed stamp shows (its stamp undone or deleted) is stored anew.
- **Difference recorded:** MuPDF reuses an image by digest across the whole document (any XObject); here among stamps, where repeated images come from. Shared images behave as MuPDF's for redaction: `redact-preview` reports the other stamp's draw (`shared`), as for engine.ts.
- Test: `identical_stamp_images_share_one_image_object` (a stamp, a second stamp and an image signature share one object, another image does not; undo and redo exact; after undoing every stamp the image is stored anew; a stamp deleted on one page no longer offers its image, one still listed elsewhere does).

## Minors

- **Direct-dictionary annotations (annots): recorded, unchanged.** ISO 32000 wants /Annots entries indirect; MuPDF's id 0 names whichever direct one comes first, so an edit could reach the wrong one. Already in `app-annots.md`.
- **Name and number tree pairs (annot-delete): fixed.** `pagetree::cut_references` removed a cut reference from any array, so a /Names or /Nums pair lost its value and later pairs shifted. A key whose value (or that itself) is cut now leaves with its value (`Cut::cut_pairs`, and the in-place path past the depth limit). Only malformed trees name annotations. Test `a_delete_cuts_a_name_or_number_tree_pair_whole` (`/Names [(a) 5 0 R (b) 6 0 R]` → `[(b) 6 0 R]`, `/Nums [0 5 0 R 1 6 0 R 2 [5 0 R 6 0 R]]` → `[1 6 0 R 2 [6 0 R]]`, undo exact).
- **Stamp without an appearance (annots, annot-set) and FreeText move without an appearance (annot-move):** fixed with the fit and the fonts above.

## Round 3 minors

October 16, 2026 (branch `app-p8-fix-minors` on 46f1e95). The minor findings the final review left open on the annotation ops.

- **No-break space and soft hyphen (annot-add): fixed.** `forms::text::win_ansi_code` is built from WinAnsi's glyph names, where 0xA0 is `space` and 0xAD `hyphen`, so U+00A0 and U+00AD had no Latin code and went to `HelvCYR` (nbspace) and `HelvGRK` (sfthyphen). They are now 0xA0 and 0xAD, one `/Helv` run as MuPDF writes it (widgets too). Unit test `free_text_keeps_winansi_spaces_skips_ignorables_and_composes_marks`; native `free_text_draws_format_characters_as_nothing_and_composes_accents` (a no-break space draws as a space).
- **Zero-width and format characters drew `?` (annot-add): fixed.** `forms::scripts::drawn` leaves out default-ignorable code points (Unicode's Default_Ignorable_Code_Point set: U+200B-U+200F, U+2060-U+206F, U+FEFF, U+FE00-U+FE0F and the other ranges listed in `ignorable`), C1 controls (U+0085 among them) and U+2028-U+202E, before layout; MuPDF draws nothing for them. The soft hyphen is not left out: WinAnsi draws it, as MuPDF does. Combining marks are composed with the letter before them when a font has the result (Unicode canonical composition for the letters of WinAnsi and `LATIN_EXTENDED`, read from their Adobe glyph names, plus Greek tonos and dialytika and Cyrillic й, ё, ї); MuPDF draws the base letter and nothing for the mark, so NFD text (macOS file names) keeps its accents here. A mark with nothing to compose with is still `?`. Recorded in `app-annots.md`. Both rules serve widgets as well (shared `scripts::lines` and `scripts::encode`). Tests: the unit test above (U+200B, U+FEFF, U+2028, U+0085, U+200D, U+FE0F; é, ż, ș, ț, ά, й; `q` + U+0301 stays `?`); native `free_text_draws_format_characters_as_nothing_and_composes_accents` (the reopened save draws `a`U+200B`b`U+FEFF` c`U+200D`d`U+FE0F pixel-identical to `ab cd`, `Cafe`+U+0301 to `Café`, `z`+U+0307 to `ż`).
- **Dashed FreeText border regenerated solid (annot-set): fixed.** `appearance::free_text` writes the /BS dash pattern (`annots::border_dash`, the one shapes use) before the width, as MuPDF writes `[3 2]0 d`. It serves annot-set, annot-move of a FreeText without an appearance and the view's synthesis. Unit test `a_dashed_free_text_border_stays_dashed`; native `a_dashed_free_text_border_is_regenerated_dashed` (`/BS << /W 2 /S /D /D [3 2] >>`: the regenerated stream holds `[3 2]0 d`, the view draws gaps in the top edge, undo exact).
- **FreeText /DS ignored (annot-set): recorded** in `app-annots.md` with the review's corpus measurement (35 of 313 FreeTexts carry /DS, 9 with a DS colour other than the DA's, in 2 files; the original appearance used the DA colour in 5 of 8). Reading the DS colour and size as MuPDF's rich path does is left: it means parsing CSS-like text and matching MuPDF's rich-text metrics (the 1.1 pt baseline shift), more than a minor fix, and the DA choice matches most of the original appearances.
- **DA font names beyond MuPDF's five (annot-set): recorded** in `app-annots.md`: HeBo, TiBo, TiIt and the other Helvetica, Times and Courier abbreviations draw their own face (MuPDF: Helvetica), /Symb and /ZaDb draw Helvetica (MuPDF: symbol glyphs). Kept on purpose: the author's style shows and typed text stays readable.
- **Direct-dictionary annotations (annots): unchanged, already recorded** (`app-annots.md`, round 1 above). The review accepts it as recorded; addressing a lone direct annotation by its /Annots index would add an id scheme the adapter and renderer do not have.
- **A cut inside a /Nums value array shifts later items (annot-delete): skipped.** Only malformed trees list an annotation inside a ParentTree value array. Writing null there instead would change `pagetree::Cut`, which field-delete, page deletion and redaction share, for a case no corpus file has; the review marks it optional.
