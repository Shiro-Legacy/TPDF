# Navigation op group: bookmarks and links

`src/app/ops/nav.rs` (with `nav/outline.rs`, `nav/links.rs`, `nav/target.rs`) implements `outline`, `outline-add`, `outline-set`, `outline-delete`, `links`, `link-add`, `link-delete` and `link-set` on `AppSession`, with engine.ts's check order, messages (plain, except `checkPage`'s and `requireMutable`'s tagged ones and link-set's `invalid` + `detail`), reply fields and step names (`add bookmark`, `rename bookmark`, `delete bookmark`, `add link`, `delete link`, `edit link`). Every write is one `AppSession::mutate` step through `Transaction` (or any `Edit`), so undo, redo and abandon restore exactly; `tests/app_nav.rs` checks each op and a random edit sequence against a full rewrite of the starting state.

## Design

- **Targets** (`target.rs`). `Resolver::link` reads /Dest, else /A, else /AA /U, else /AA /D (MuPDF `pdf_load_link`); `Resolver::outline` reads /Dest, else /A. The result is `Target::Page(i)` only for a local destination naming a page of this document (explicit `[page ...]` with a page reference or an integer in range, or a name/string found in /Dests or the /Names /Dests tree, via `pagetree::dest_page`). Everything else with a MuPDF link URI is `Target::Uri`: URI actions (relative ones prefixed with /URI /Base or `file://`), GoToR and Launch (`file:` + percent-encoded path, /UF before /F), and dead local destinations (`#page=N&view=...`, `#nameddest=...`). Named FirstPage/LastPage are pages; PrevPage/NextPage are pages for links (from the link's page) and nothing for bookmarks. JavaScript, Named Print and the like have no target: the link is not listed, the bookmark has `page: null` and no `uri`. URI strings are MuPDF's `getURI` strings (checked against MuPDF 1.28.1 for every kind `tests/app_nav.rs` lists).
- **Links** (`links.rs`). A link is a /Annots entry with /Subtype /Link, a /Rect array and a target, in /Annots order. Its `annotId` is the entry's own object number (0 for a dictionary written into /Annots), exact rather than paired again by rect. `PageSpace` is MuPDF's `pdf_page_transform` as the view's `PageFrame` computes it (CropBox within MediaBox, UserUnit, /Rotate snapped); rects agree with MuPDF's `getLinks` on rotated, cropped and scaled pages. `checkLinkRect`'s page box is `info::page_size`.
- **link-add** writes `<< /Type /Annot /Subtype /Link /Rect /BS << /Type /Border /S /S /W 0 >> /A /P >>`, the action `<< /S /GoTo /D [page /Fit] >>` or `<< /S /URI /URI (text string) >>`, appended to the page's /Annots (made an array when it is missing or not one). **link-set** writes /Rect and/or replaces /A and drops /Dest, only what changed; a request within 0.01 of the current rect and with the current target answers `noop` with no step. **link-delete** removes the listed entry by its /Annots position.
- **Outline** (`outline.rs`). `Outline::read` walks /First and /Next from /Outlines in preorder with an explicit stack; an item object already walked is not walked again. Items may be dictionaries written into other items (`edit::Place`). Ids are preorder indices.
- **Outline edits** keep the tree as walked consistent: outline-add appends after the walk's last top-level item (/Prev, the old last's /Next, the root's /First and /Last); outline-delete links the neighbours (/Next, /Prev) and fixes the parent's /First and /Last. Then /Count is rewritten from the structure on the edited item's parent, every item above it and the root: the visible descendants, negated for a closed item (open = has children and /Count > 0), absent on an item left without children; the root's is absent when nothing is visible. Values already right are not written. An item or root the edit must name by reference that is a direct dictionary is given its own object first, in the same step.
- **Direct pages.** A link or bookmark to a page written directly into /Kids, or a link added to one, first gives the page its own object (`links::page_object`, after `pagetree::normalize`), in the same step.
- **Bounds.** The walk and the link list are linear in the objects of the document. The `outline` and `links` replies list at most `MAX_LISTED_ITEMS` (100,000) entries; ids past that still name items for the edit ops.
- Reusable by other groups: `links::list`, `links::add`, `links::set`, `links::remove`, `links::page_object`, `links::PageSpace`, `target::Resolver`, `outline::Outline`, `nav::link_json`, `nav::scheme_of`.

## Differences from MuPDF and engine.ts

- A URI is never resolved back to a page. MuPDF's `resolveLink` reads the fragment of any URI, so `https://x/#page=3` listed as `kind: "page"` page 2, a GoToR (`file:other.pdf#page=1`) as page 0 of this document, and a URI action `#page=2` as page 1. Here they are `uri`/`blocked` with MuPDF's URI string.
- A destination that names no page (a dangling or non-page reference, null, a real, an integer out of range) is `blocked` (link) or `page: null` with its `uri` (bookmark). MuPDF lists references as page 0 ("#page=1"), drops an out-of-range integer link, and an out-of-range integer in any bookmark made `loadOutline` throw, so engine.ts listed no bookmarks at all.
- outline-set writes only /Title. MuPDF's iterator update dropped /C and /F, rewrote `/A /GoTo /D [p /XYZ 10 700 0]` as `/Dest [p /XYZ 10 700 null]`, turned a GoToR into a local `/Dest [0 /Fit]` and deleted Named and JavaScript actions.
- The first bookmark creates `/Outlines << /Type /Outlines /First /Last /Count 1 >>`; MuPDF writes `/Count -1`. Counts on the edited chain are recomputed from the tree, so they are right after an edit even when the file's were wrong; MuPDF adds or subtracts from the stored values along /Parent.
- outline-add appends after the last top-level item the walk lists and outline-delete relinks the walk's neighbours; MuPDF's iterator follows the stored /Prev, /Parent and /Last. A /Next cycle or a shared item is cut where the walk stops.
- An item reachable twice (a /First or /Next shared by two parents) is listed once, at its first preorder position; MuPDF lists it under each parent (its marks only catch cycles), which a crafted outline can make exponential.
- link-add writes /P (the page), as Acrobat does; MuPDF's `createLink` writes none.
- link-delete removes the exact /Annots entry listed (MuPDF removes the first entry equal to it). When no page lists the annotation any more, references to it are cut (`pagetree::cut_references`): a structure OBJR, another annotation's /IRT or /Popup, so a save does not keep it; MuPDF leaves them, and the annotation is still written.
- `annotId` is exact: a link with a non-numeric or short /Rect still has its object number (engine.ts gave 0 when its rect pairing failed), and link-set accepts it. A link whose /Rect is not an array is not listed; MuPDF lists it with an infinite empty rect.
- A Launch action's URI has no fragment (`file:app.exe`); MuPDF appends `#page=1`.
- Rects are computed in double precision from the page boxes as MuPDF reads them (single precision), so they differ from MuPDF's single-precision results only by float rounding. A negative zero is reported as 0.
- The `outline` and `links` replies stop at 100,000 entries; MuPDF lists everything (a few MB of object streams can hold 2 million items, whose JSON reply would exhaust the WASM heap).
- A title is stored as given (`encode_text_string`: ASCII, else UTF-16BE), NULs included; MuPDF's C strings cut it at the first NUL. A URI keeps MuPDF's text-string encoding (UTF-16BE when it is not ASCII) so it reads back as the app sent it.
