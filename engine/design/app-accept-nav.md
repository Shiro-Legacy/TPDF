# Acceptance review: outline, outline-add, outline-set, outline-delete, links, link-add, link-set, link-delete, labels, labels-set, labels-clear (round 1)

October 16, 2026. Fixes for the acceptance review of the navigation and label ops at ed62a16 (accepted: outline-add, outline-set, outline-delete; not accepted: the other eight). Read with `app-nav.md` and `../APP-ENGINE-DESIGN.md` (labels). Regression tests: `tests/app_accept_nav.rs`.

## Trees whose /Kids array names itself (blockers: outline, links, link-set, link-delete, labels, labels-set, labels-clear)

- **Verified.** Cause as reported: `pagetree::name_tree` and `labels::entries` remembered only nodes held by references. A direct node inside a /Kids array object that its nodes name again was walked again to depth 64: 2^64 visits on the reviewer's 581-byte names-bomb.pdf; labels-bomb.pdf (456 bytes) grew `order` until the WASM heap trapped. Acyclic trees that reuse one array object per level grew 2^depth.
- **Fix.** `pagetree::tree_nodes` (and `forest_nodes` for an array of roots): preorder, each object entered once, as a node or as a /Kids array (`resolve_with_holder`), so a direct node is reached only through the one walk of the array that holds it. Linear in the document; also at most 64 levels and `MAX_TREE_NODES` (2^20) nodes. The order is unchanged (a node, then its /Kids in order): the first of equal names wins, the later of equal label keys is last. The tree's root is passed as stored (`pagetree::stored`), so a kid naming the root object is skipped too.
- Users: `name_tree` (every `NamedDests::load` caller: links, link-set, link-delete, outline, page-delete's link repair, graft), `labels::entries` (labels, labels-set, labels-clear, stamp `{label}`, the page ops' label adjustments).
- **Same class outside the nav ops** (found while verifying; each stopped the open): `info::detect` counts attachments (/Names /EmbeddedFiles, now `tree_nodes`) and signatures (/AcroForm /Fields, now `forest_nodes`) on every open; both hung on the same shape. `info::walk_tree` (the page list) grew past 2 GB within a second on a /Pages /Kids array object whose direct /Pages nodes name it again; it now enters each /Kids array object once (pages and nodes held by references were already entered once, so no page list of a well-formed tree changes). The forms group's field walks (references only, a visit limit) and the redaction inventory (refuses past its bound) were already bounded.
- **Differences** (both from reading every node, which ed62a16 already did, now recorded): names-bomb's link and bookmark go to page 0, since (a) is defined in a leaf; names are read from every leaf, direct ones included, whatever its /Limits. MuPDF skips a direct internal node ("non-indirect internal node found in name tree") and bisects the kids by /Limits, so it lists `#nameddest=a` (link `blocked`, bookmark `page: null`). labels-bomb lists `["i"]` (its one range); MuPDF's label lookup recursed until the stack ran out, so engine.ts listed `["1"]` and refused labels-set and labels-clear ("Maximum call stack size exceeded").
- Tests: `a_name_tree_whose_kids_array_names_itself_is_walked_once` (names-bomb: 3 nodes; links, link-set, link-delete, undo; names-bomb-outline), `trees_whose_paths_double_per_level_are_walked_in_linear_time` (60 levels, 2^60 paths, 121 nodes; labels and links), `a_number_tree_whose_kids_array_names_itself_reads_and_edits` (labels-bomb: labels, labels-set, labels-clear, undo), `other_trees_whose_kids_array_names_itself_open` (attachments, signatures, page tree; open, the listings and render).

## Shared /Annots arrays (link-add blocker)

- **Verified**: three pages naming one /Annots array object, link-add on page 0 listed the link on all three and saved it so.
- **Fix** (`links::own_annots`): when another page names the same array object, the page gets a direct copy first, in the same step, and the edit goes there; the others keep the shared array. link-add now matches MuPDF (links per page 1, 0, 0).
- link-delete (and the edit group's link removals through `links::remove_many`) does the same, so a link deleted on one page stays on the others, and the annotation is kept while a page lists it. **Difference**: MuPDF, and ed62a16, removed it from every page sharing the array (the reviewer judged that no regression); with link-add copying, both edits now change only the page they name.
- annot-add has the same behaviour (`annots::edit_annots`, annotations group): not changed here, routed to its owner.
- Test: `link_add_and_delete_on_a_shared_annots_array_change_only_their_page` (listings, the arrays, the saved file reopened, undo to the exact start; an unshared array object is still edited in place).

## An update glued to %%EOF (major, open and repair)

- **Verified** natively on glued.pdf's structure. Two causes: the strict reader's `section_footer` refused anything but whitespace after `%%EOF` ("section %%EOF delimiter"), so the file went to the rebuild; the repair scan's `object_header` wanted a delimiter before the object number, so `%%EOF1 0 obj` was no object and the rebuild kept the older catalog (and was `damaged`, so `repaired: true`).
- **Fix, strict reader** (`document.rs`): a section ends at its `%%EOF` when something else follows on the line. The existing check between physical regions then requires an indexed object or section to begin exactly there, so unindexed data after the marker is still refused. The file opens strictly, unrepaired, with its two sections, as in MuPDF.
- **Fix, repair** (`repair.rs`): an object number directly after `%%EOF` starts an object header, for a file that also needs repair for another reason.
- Test: `an_update_whose_first_object_follows_eof_on_its_line_is_read` (strict open, versions as the unglued file, the bookmark listed and kept by an unedited save; a wrong final startxref repairs and keeps it; `%%EOFjunk` still refused strictly).
- Corpus: see Measured. The corpus differential's missing class (a Rust-only repair that loses catalog keys) belongs to the evidence tooling and is not added here.

## Minors (labels-set)

- **Starts past 2^31 - 1** are refused after engine.ts's own checks, plain: "labels-set: start must be at most 2147483647". **Difference**: engine.ts took any integer; MuPDF passed it on as a C int (2^53 became 0, so no /St; 1e20 wrapped), and readers take /St as an int. Reading stays 64-bit (recorded in APP-ENGINE-DESIGN). `tests/app_pages.rs` `odd_trees_and_hostile_sources_never_panic` sent 2^53 - 1 and expected success; it now sends 2^31 - 1, the largest start taken (a test of this rewrite encoding the old behaviour). Test: `label_starts_past_a_32_bit_int_are_refused`.
- **/PageLabels naming no number tree** (`labels::foreign`: the catalog, the /Pages root, or a dictionary typed /Catalog, /Pages or /Page) lists no labels, and labels-set writes a new tree into the catalog, as `outline::foreign` treats such an /Outlines. A /PageLabels dictionary with keys other than /Kids, /Nums, /Limits and /Type (a field, a font) is still read as a number tree but never rewritten: the catalog gets a new tree. So the session and the save agree. **Difference**: MuPDF wrote /Nums into the page tree root (and broke the page tree). Test: `page_labels_naming_the_page_tree_or_a_field_are_never_written_into`.
