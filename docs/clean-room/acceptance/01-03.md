## Open issues

1. Spec 02 §4 says `<~87cURD…~>` fails with `InvalidByte('<')`, but `<` is
   a base-85 digit under §3.4, which makes the `~` after it an
   `InvalidEndMarker` (the current engine's answer). The test accepts
   either; the spec should pick one.
2. The current repair does not locate `startxref` with
   `incremental::startxref` (N15: a hybrid followed by 3,000 NUL bytes is
   reconstructed). The rewrite must use the shared locator (§4.3).
3. `app_corpus_open.rs`
   `objects_appended_without_an_xref_leave_the_last_complete_revision`
   still pads 1,100 bytes to pass the locator's window. If R7 re-derives a
   window longer than that, the pad must grow; `app_sign.rs` and
   `cleanroom_repair.rs` N14 already derive the window from
   `incremental::startxref`.
4. N9 covers AES-128 and AES-256 object streams only; `tests/data` has no
   RC4 object-stream file. Those `tests/data` files were generated with
   MuPDF used only as a writer (`engine/oracle/generate-encrypted-cases.mjs`),
   like the spec's `h-*` inputs; the owner should confirm they may be
   handed over.
5. `app_core.rs` still has MuPDF comments outside specs 01 to 03 (around
   the trailer Info, free-entry, password-byte and owner-password tests),
   and `app_sign.rs`/`document_app.rs` keep a few writer comments that cite
   "another viewer". They belong to no clean-room workstream, but they go
   into the hand-off tree with these files.
6. Spec 01 Appendix C asked whether the /Type,/Subtype rule applies to
   stream dictionaries; S3 says yes, and
   `stream_dictionaries_put_type_and_subtype_first` expects
   `/Type /Subtype` first, then the others in order, with `/Length` in
   place or last.
