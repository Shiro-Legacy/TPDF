# P6 U7 — objects on the page IV: Cut / Copy / Paste of everything selectable on the page (images, forms, text runs, fields, links, redaction marks); multi-select of text runs, fields, links and marks

Drafted 2026-09-24 by fable51 after U6 acceptance (progress.md §6 "P6 U6"). Lean mode, Opus 5.5 subagents, no fixture phase. **Decisions for the human (D1–D5); each is built as written unless changed:**
- **D1 — clipboard scope:** one clipboard per worker, held in the engine session as a scratch `PDFDocument` with the copied XObjects grafted into it plus the placement facts (§1.1). It survives `close` and `open` of another PDF while the worker lives (renderer.ts:762 creates the worker once; :840 terminates it only on a worker failure), so copy in one document and paste in the next works. It is never the system clipboard (§7). Lazier alternative: per-document only (cleared on `open`) — saves the scratch document, loses cross-document paste.
- **D2 — paste placement (amended by §9.3/§9.28–§9.29):** the clipboard moves as ONE group by one delta. With `at` (the page menu), the delta puts the top-left of the union of the visible boxes at the click point; otherwise the delta starts at (0,0) and, while a candidate already occupies any item's target box (±0.5 pt), steps like menu Duplicate (`menuDuplicateRect`, renderer.ts:2790-2793: +10 x, −10 y in page points = +10 right, +10 down on screen; −10 x when x1+10 exceeds the page width, +10 y when y0−10 is below 0), at most 20 steps; the delta is then shifted so the union lies inside the page clip; `out-of-bounds` only when the union is larger than the page. So Cut then Paste restores in place, a repeated paste cascades, and a paste into another document lands at the source box. Keyboard paste (D5) sends no `at`. Lazier alternative: no occupancy check, always offset on the source page — simpler engine, but Cut+Paste lands 10 pt off.
- **D3 — no new fixture.** Proof on `fixtures/p6/objects6.pdf` (page 1 owns a different `/Im1` 6×3, so a paste from page 0 must take a fresh name), `fixtures/p3/edit-objects.pdf` → `objects6.pdf` cross-document, `fixtures/p6/direct3.pdf` (text runs + images), `fixtures/p3/field-defs.pdf` (fields), `fixtures/p6/links.pdf` (links), marks drawn by the drive on `fixtures/hello.pdf`. `checks/fixtures.sha256` stays 9 lines; `u7-hash-before.txt` = `u6-hash-after.txt` (55) and nothing may be added.
- **D4 — Cut/Copy/Paste work for everything selectable on the page** (decided by the human 2026-09-24, replacing "images and forms only"): images and forms (§1.1–§1.2), text runs, fields, links and redaction marks (§10). Copy is one `clip-copy` over the whole selection; Paste is one `clip-paste` = one journal op, all-or-nothing except the link rule in §10.6; Cut = copy, then one delete batch of every member that can be deleted (text runs cannot: they stay, and the announcement says so, §10.8). §10 overrides §1, §2, §4, §7 and §9 wherever they differ.
- **D5 — ⌘X/⌘C/⌘V** stay Edit-menu roles (src/main.ts:1067-1069 untouched); Electron's `role: 'copy'` runs `webContents.copy()`, which dispatches the DOM `copy` event in the renderer (proven by both objection lenses on Electron 44: `webContents.copy()/cut()/paste()` and CDP `Input.dispatchKeyEvent` with `commands:['copy'|'cut'|'paste']` fire the events on the focused object button and on `body`; a plain CDP Meta+C fires nothing). The renderer handles `document` `cut`/`copy`/`paste` events under one exported pure predicate `clipboardChordOk` (§9.24) and lets them through otherwise. GUI evidence uses CDP keys with `commands`; the native accelerator → role path is proven once by fable51 with a real AppleScript keystroke at acceptance (§6.3).

## 1. Engine (`src/renderer/engine.ts`, `engine-core.ts`, `content-edit.ts`)
### 1.1 Clipboard and `clip-copy`
`Session` gains `clipboard: { doc: PDFDocument; items: { kind: "image" | "form"; name: string; orient: EditOrient; visible: number[]; full: number[] | null; object: number }[]; source: { name: string; page: number } } | null` (module-level in the worker session, not per document; `close` leaves it alone; `doc` is a scratch `new mupdf.PDFDocument()` that lives as long as the clipboard). `ClipCopyRequest { id; op: "clip-copy"; page; generation; revision; targetIds: string[] }`: check order — `allowed(session.info, "copy")` (an encrypted document without the copy bit refuses with the same token `requireMutable` gives a denied op, engine.ts:1537), `checkPage`, shape (`targetIds` 1..`MAX_EDIT_TARGETS` non-empty distinct strings, else `invalid-selection`), then per id `resolveEditTarget` (`stale-target`, `too-large` as U5) and candidate `image|form` with a top-level simple `placement` (else `not-candidate` with `targetId`). Then, with nothing written to the document and no journal op: build a fresh scratch document, graft each placement's XObject (`at(at(pageResources,"XObject"), name)`) into it with one `newGraftMap()` per copy (a form's own `/Resources` travel with the graft; `pdf.newGraftMap().graftObject` is the pattern at content-edit.ts:1223), record `{kind, name, orient, visible, full, object: copy.asIndirect()}`, and replace the previous clipboard wholesale (its scratch document is destroyed). Reply `{ ok: true, count, kinds: { image, form } }`; `revision`/`dirty` unchanged. Byte budget: the grafted streams are charged like `editPrivatise`'s `charge()` and `too-large` refuses before the clipboard is replaced (the old clipboard survives a refusal).
### 1.2 `clip-paste`
`ClipPasteRequest { id; op: "clip-paste"; page; generation; revision; at?: [number, number] }` (`at` in page points, bottom-left origin: the box's top-left corner, D2). Check order, every check before any write: `requireMutable` (`read-only`), `checkPage`, `empty-clipboard` when `clipboard` is null, `invalid` when `at` is not two finite numbers, then per item: target visible box = the source box translated to `at` when given, else the source box, then D2's Duplicate offset when `session.name === clipboard.source.name && page === clipboard.source.page`, then `editObjectBox(box, pageClip)` (`out-of-bounds` when the box cannot fit the page at all), then `full` = the clip-less full box implied by the visible box and `orient` (U6 `editPlacementAfter`), `editCheckFull` (`too-large`); cap: `editScanFor(session, page).size + items.length > MAX_EDIT_TARGETS` → `too-large`. Then ONE `mutate(session, doc, "paste objects", …)`: give the page its own `/Resources` when inherited (the `text-add` copy at engine.ts `case "text-add"` — same code path, shared helper), a fresh `/XObject` name per item — `PA<n>`, `n` the first integer from 1 not present in the page's `/XObject` dict (never the source name: objects6 page 1 owns a different `/Im1`), graft the scratch object into the document (`pdf.newGraftMap().graftObject(clipboard.doc.…)`; one map per paste so a shared SMask inside one paste is grafted once), and append to the page's last `/Contents` element (privatised first when another page shares it, exactly as `editPrivatise` does for `sharedContents`; an empty page gets one new stream) one block per item: `"\nq\n" + (clip ? "x y w h re W n\n" : "") + "a b c d e f cm\n/PA<n> Do\nQ"` with the `cm` the U6 writer produces for that `orient` and full box and the clip = the visible box (the U6 §1.1 text, so the block scans back as a candidate with `orient`/`full` intact). Reply `{ ok: true, page, count, names: string[], …editState }` (`revision` +1, `dirty` true); the new blocks are candidates with every image/form `objectOps` (`move, resize, delete, replace, duplicate, transform, crop` for images); undo removes them in one step and restores the bytes; save→reopen keeps them. **Cut** is renderer-side: `clip-copy` then the existing delete (`edit-object delete` or `edit-objects` delete items) — one journal op, the existing tokens, no `object-cut` op.
### 1.3 `edit-batch` — one journal op over mixed kinds
`EditBatchRequest { id; op: "edit-batch"; page; generation; revision; items: BatchItem[] }` with `BatchItem =` `{ op: "edit-text"; targetId; text; move?: {dx,dy}; size? }` | `{ op: "field-props"; widgetId; rect }` | `{ op: "field-delete"; widgetId }` | `{ op: "link-set"; annotId; rect }` | `{ op: "link-delete"; annotId }` | `{ op: "redact-set"; annotId; rect }` | `{ op: "annot-delete"; annotId }` | `{ op: "edit-object"; targetId; action: "move" | "delete"; box? }`. Order: cap (`items.length > MAX_EDIT_TARGETS` → `too-large`), shape / fewer than two items / a repeated id within a kind (`invalid-selection`), then per item its own permission (`allowed(session.info, OP_PERMISSION[item.op] ?? "edit")`, refusing with the single op's own token and the item's `index`), then per item the single op's own planning and refusal (every existing token, carried with `index` and the item's id; `edit-text` items are the U2 move path with the run's own `text`), then ONE journal op `"edit batch"` that runs the items' write parts in order. Implementation rule (choose the smaller diff, state it in the evidence file): `mutate` gains one branch — while `session.batch` is open it runs `work()` and returns without touching the journal (the batch handler owns `beginOperation`/`endOperation`/`abandonOperation` and the `savedPosition` bookkeeping of engine.ts:1732-1755) — and the batch dispatches each item to the existing case bodies (factored into functions where a case is not callable). Any throw inside → `abandonOperation`, nothing written (proven by page bytes and `/Annots`), reply carries `{ reason, index, targetId|widgetId|annotId }`; `revision` +1 only on success; the reply is `{ ok: true, page, count, …editState }`. Objects-only selections keep using `edit-objects` (U5, unchanged); `edit-batch` is used when the selection has any non-object member.

## 2. Renderer (`src/renderer/renderer.ts`, `index.html`, `styles.css`)
### 2.1 Cut / Copy / Paste (menu, chords)
`#object-menu` (index.html:218) gains `object-menu-cut`, `object-menu-copy`, `object-menu-paste` **before** `object-menu-replace` (11 items; the eight U5/U6 ids and their order unchanged). `objectItemsFor` (renderer.ts:2744) gains `cut: every("delete") && copyOk`, `copy: copyOk` where `copyOk = list.length > 0 && list.every(t => t.item.kind !== "text") && permitted("copy")`, `paste: canEdit() && !!clipboardInfo`. `clipboardInfo: { count: number; kinds: { image: number; form: number } } | null` is set from the `clip-copy` reply and never cleared by `open` (D1). **Empty-space menu:** right-click, Control-click or Shift+F10 in Edit text with no object under the point opens the menu with only Paste enabled (`objectMenuState()` → `{ name: "", kind: "page", count: 0, items }`); its Paste sends `at` = the click point in page points (D2). Copy: `clip-copy {targetIds}` for the selection → `clipboardInfo`, announcement "Copied N objects", no `content.edited` change. Cut: copy, then the existing single/group delete (one journal op; `content.edited` as a delete). Paste: `clip-paste` → the pasted objects become the selection by `names[]` from the post-reply scan (anchor = last), Inspector synced (`syncObjectInspector`), `content.edited { kind: "objects", action: "paste", name: names.join(","), count }` (a single paste still carries `count`, since `kind:"objects"` is the U5 group shape). **Chords (D5):** `document.addEventListener("copy"|"cut"|"paste", …)` — act only when `directFocusedObject` is set, `uiMode === "edit"`, no object menu open and `document.activeElement` is not an input/textarea/select/contenteditable; then `preventDefault()` and run the menu action; otherwise return without touching the event.
### 2.2 Multi-select of text runs, fields, links and marks
`directSelection` members are `{ kind: "object" | "text" | "field" | "link" | "mark"; name; targetId; rect }` — `targetId` is the engine id for objects and text runs and `String(widgetId | annotId)` for the rest (STATE keeps `{targetId, kind, name}`; `name` = the object name, the run's first 12 characters, the field name, `link <id>`, `mark <id>`). Shift-click toggles membership on `.text-target`, `.field-target`-equivalent widgets (Fill forms), `.link-target` and `.redact-target` exactly as U5 §2.1 does on objects, **without** opening the inline editor, link form or note; members must share the page and the layer of the current mode (Edit text: text runs, objects, links; Fill forms: fields; Annotate: links; Redact: marks); a mode change, page change or Escape clears the selection; a plain click selects one. The anchor (last member) drives the Inspector as a single focus of that kind does today. `.multi` outlines on every member; `.group-box` on the union with **hidden handles** when any member is not an object (no group resize, U6 §2.2 stays objects-only).
### 2.3 Group gestures on mixed selections
Drag on any member, plain arrows (1 pt) and Shift arrows (10 pt) move the whole selection: one `edit-batch` (§1.3) with `edit-text {move}` for runs, `field-props {rect}` for fields, `link-set {rect}` for links, `redact-set {rect}` for marks, `edit-object {move, box}` for objects; objects-only selections keep `edit-objects`. Delete/Backspace → one `edit-batch` of deletes (`field-delete`, `link-delete`, `annot-delete`, `edit-object delete`); when the selection holds a text run, Delete is refused on the page ("Text runs cannot be deleted; deselect them first", live region, no request). Enter and double-click act on the anchor only (U5). ⌥-drag duplicate and the U6 transform/crop items are objects-only: the menu's `duplicate`, `rotate*`, `flip*`, `crop`, `replace` are false when any member is not an object. `content.edited { kind: "selection", action: "move" | "delete", name: <anchor name>, count }`. Refusals: `content.refused[].detail` = the item's token; `CONTENT_DETAIL_TEXT` gains `empty-clipboard` ("Nothing to paste") only. Snap guides (U6 §2.4) apply to the union rect as for object groups.
