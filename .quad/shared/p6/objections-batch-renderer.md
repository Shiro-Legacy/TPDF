**R-1 (blocking) §4.1, §4.2, D1** — The listing order is not defined, and the expected Bates mapping is wrong. Node `readdir` does not sort. Amendment: "`pick-folder` sorts the names with `a.localeCompare(b, 'en', { numeric: true, sensitivity: 'base' })` before it replies, and that order is the queue and Bates order. §4.2 expects `B-0001` hello, `B-0002…B-0004` nav (3 pages), `B-0005` rotated (1 page); `batch.files` order is encrypted, hello, nav, rotated."
**R-2 (blocking) §4.1, D3, D5** — A drive cannot pass `--batch-dir=`. scripts/drive.mjs:44-46 forwards only `--gui`, and p6-drive8's `drive()` (:28-31) passes no extra flags, so "as p6-drive8's drive() helper does for other flags" is false. The existing pre-answers are top-level line keys that main reads in `startDrive` (main.ts:1719-1721: `to`/`from`/`images` → `saveToArg`/`insertFromArg`/`imagesArg`). Amendment: "main.ts:42 area gains `let batchDirArg = process.argv.find(a => a.startsWith('--batch-dir='))?.slice(12);`. `startDrive` gains `if (args.dir !== undefined) batchDirArg = pathOf(args.dir);` next to :1720. The drive line is `{\"cmd\":\"batch\",\"dir\":\"${OUT}/batch-in\",\"contents\":{\"kind\":\"footer\",\"text\":\"B-{bates}\",\"align\":\"right\",\"batesPad\":4},\"expect\":{…}}`. The contents key `folder` is dropped, because the renderer never names a path. scripts/drive.mjs is untouched. The test's copied `drive()` creates its tmp dir, copies the four fixtures into `<dir>/batch-in`, then spawns with `--out=<dir>`."
**R-3 (blocking) §3.3, §4.1** — `decorate.bates.next` will not appear after a batch. `decorate` is emitted only when `decorateSummary` is set (renderer.ts:7916), and Bates §9.13 keeps it that way ("absent until the next decorate action"). The drive session has only the startup hello.pdf and no decorate action, so §4.1's `decorate.bates.next = 6` fails even when the batch works. Amendment: "STATE `batch` gains `bates: { start: number, next: number, pad: number }` (next = the module `batesNext` after the run). §4.1 pins `batch.bates {start:1, next:6, pad:4}` and does not read `decorate`."
**R-4 (blocking) D2, §3.2** — With the default timeout, a slow file drops the human's open document. `request()` defaults to `REQUEST_TIMEOUT_MS` = 20 s (renderer.ts:165). When that timer fires it calls `workerFailed` (:813-814), which terminates the worker and calls `resetDocument()` (:850-852). A long batch-file on a large (up to 120 MiB) PDF therefore silently closes the open document and its undo stack, which contradicts D2. Amendment: "`batch-file` is requested with `SAVE_TIMEOUT_MS` (renderer.ts:167, as insert-pages at :7227). A timeout then rejects without killing the worker (:808-811): the row fails with 'the request took too long and was stopped', and the queue stops (cancelled true)."
**R-5 (blocking) D2, D5** — The cited precedent refuses when no document is open. insert-pages (engine.ts:5115-5116, not :5103) starts with `requireMutable(session, …)`, which throws `no-document` (:1589-1591). With `OP_PERMISSION "any"`, it would also check the HUMAN's document permissions (:1595). The precedent that needs no document is `pdf-from-images` (engine.ts:5204), which is listed in p2-shell READ_ONLY (:167-171). No drive or GUI step can prove the no-doc path either, because every drive opens the fixture first (main.ts:1703 awaits P1_RESULT). Amendment: "`batch-file` follows `pdf-from-images`: it never calls `requireMutable` or reads `session.doc`. It has no `OP_PERMISSION` row and is added to `READ_ONLY` in tests/p2-shell.test.mjs:170. Engine test (e): a fresh session with no `open` runs batch-file on nav.pdf → ok. Test (f): a session holding `encrypted-noedit.pdf` (no edit permission) still runs batch-file on nav.pdf → ok."
**R-6 (should) §2.3** — There is no main-side channel-pin file. `grep -rln pick-images tests/` finds only a comment (p6-drive3.test.mjs:49) and drive JSONL. No p1-main exists. The only main-source reader is `mainSrc()` in p2-shell.test.mjs:14, and no contextBridge allowlist test exists. Amendment: "The path rules are one exported pure function in src/policy.ts, `batchOutName(name: unknown, listed: ReadonlySet<string>): string | undefined`. It returns the name only when it is `'report.txt'` or a listed name, `basename(name) === name`, and it is not `.`/`..` and ≤ 255 chars. p6-batch.test.mjs imports it from build/policy.js and tests `../x.pdf`, `a/b.pdf`, `..`, an unlisted `x.pdf`, a listed name and `report.txt`. p2-shell adds source pins: `ipcMain.handle('pick-folder'` and `ipcMain.handle('batch-io'` each followed within 2 lines by `if (!isTrustedOpen(event))`, and `accelerator: 'Alt+CmdOrCtrl+B'` exactly once in main.ts."
**R-7 (should) §2.1, D3 write** — Reusing `writeNew` overwrites an existing file. `writeCopy` commits with `rename(tmp, destPath)` (safe-write.ts:222-223), which replaces the destination, so "refusing `exists`" needs its own check. `canonicalDest` realpaths the directory (safe-write.ts:55-56), so a symlinked `pdf4all-out` would send the writes elsewhere. `batch-io read` uses sizes from listing time. Amendment: "`batch-io write`: `batchOutName` first (`bad-name`), then `saveWithinCeiling` (`too-large`, policy.ts:14). `mkdir(out)` ignores EEXIST, then `lstat(out)` must be a real directory (not a symlink), else `unreadable`. `lstat(dest)` succeeding → `exists`. Only then `writeNew({dest, bytes, journalPath})`. `batch-io read` re-runs `inspectRegularFile` + `pdfWithinCeiling` on `join(folder, name)` before `readFile`, as insert-source does (main.ts:691-697). Listings live in `batchListings = new Map<number, {folder, names: Set<string>}>` keyed `event.sender.id` (the certPaths pattern, main.ts:51)."
**R-8 (should) §3.2, §4.2** — Neither the counter rule nor the second run is defined. The second run's `report.txt` also already exists. Amendment: "The renderer asks `batch-io {action:'exists', name}` (or the write refusal) BEFORE reading a file: an existing output makes the row `failed`/`exists` with no engine work. `batesNext` advances only after a successful write. Second run: 3 rows `exists`, encrypted.pdf `encrypted`, `batch.bates.next` unchanged at 6. The report write refuses `exists`, the announcement says 'report not written: report.txt exists', and `batch.out` is null."
**R-9 (should) §1.1, §3.1, D1** — Per-file page ranges cannot be parsed in the renderer. `parsePageRange(text, pageCount)` needs each file's count (engine.ts:6034, open end `3-` → pageCount :6045), and the renderer does not know it before the worker opens the file. **R-10 (should) §3.2** — Worker refusals never resolve. `onWorkerMessage` rejects every `ok:false` with `.reason` and `.reply` (renderer.ts:826-832), so "on ok … else failed" never sees a `{ok:false}` reply. Amendment: "The `#batch-dialog` `cancel` listener calls `preventDefault()` while `running` and sets `cancelled`, as `#batch-cancel` does.
