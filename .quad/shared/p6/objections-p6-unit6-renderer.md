## checkedFine (tried to break, could not)
- **Menu keyboard with 8 items (Q1).** Cycling, Home/End and Enter/Space all go through `Object.values(objectMenuButtons)` (2672-2676), so the new buttons join by being added to that map (R5 covers the role selector). The `openObjectMenu` clamp uses `offsetWidth/offsetHeight` after unhiding (2635-2637), so a taller menu stays inside `#viewport`.
- **`direct.menu.items` gaining five booleans (Q1).** No test deep-equals `direct.menu` or `items`. The only `items` pins are drive expects (direct-edit6.jsonl:44,49,57,68), which are subset matches on objects. `p6-drive6.test.mjs:79` `brief` is a message helper.
- **`gestureRect` as a pure clamp (Q1).** `gestureRect(rect, 'grip', 0, 0, {min:1, lockAspect:false, page})` already serves as one in `menuDuplicateRect` (2677). It returns the rect shifted onto the page whenever it fits, so the seat needs no `clampToPage` (the rect that does not fit is R14).
- **Group-box geometry and `direct.objects` (Q2).** `direct.objects` counts `.object-target` (7119), and `restoreDirectFocus` iterates only `.object-target` (2719), so a classless `.group-box` stays out of both. With `pointer-events:none` on the box, `elementsFromPoint(...).find(n => hitLayer.contains(n))` (1335) never returns the box, only its handles. The affine member mapping under a corner with lockAspect is plain scale-and-translate through the U5 `place` hook (2350). The 4.1 arithmetic is right: union [72,142,300,192] east to 528 gives Im1 [72,142,272,192] and Im3 [328,142,528,192].
- **`fieldTarget` in the drive `handle` op (Q2).** It is `target.closest('.hit-target')` or else the first `.hit-target` containing the point (1340). For a group member that is the member button, whose own handles are `display:none` under `.multi`. So the contract's "resolve against the group box when the hit target is a `multi` member" is needed, and it is enough.
- **⌥⌘←/→ and ⌥⌘⇧←/→ (Q2).** src/main.ts has no Alt+Cmd+Left/Right accelerator (only Alt+Cmd+Up/Down, 1228/1236). macOS reserves neither chord (Mission Control uses ⌃←/→, and ⌥⌘H is the Hide Others trap). U4 already handles ⌥⌘←/→ in the renderer for single objects, marks and fields, so progress.md §1's one-owner rule holds. Today a group ignores them (2813 `if (event.metaKey) return;`).
- **Escape order among dialogs and the menu (Q3).** The sign/verify line (1334) and then the menu branch (1336-1342) come before any crop branch placed as R7 says, so Escape closes the dialog, then the menu, then crop mode, then the selection.
- **`.selected` handles in crop mode (Q3).** A single cropping member is `.selected` and not `.multi`, so its 8 handles and grip show through `.hit-target.selected .hit-handle` (588).
- **`snapRect` in the P6_HELPERS child (Q4).** The harness stubs `document`, `Worker` and `localStorage` (p6-direct:10-31) and imports named exports from build/renderer/renderer.js. A pure `export function snapRect` beside `gestureRect` can be tested there like `gestureRect` (:63-69). New top-level `getElementById` consts resolve to the proxy `el()`.
- **Existing drives do not change under snapping (Q4).** I recomputed every object drag and handle step with direct3's view rects (Im1 [72,142,172,192], Im2 [400,52,460,92], Fm1 [400,262,500,292], page 612×792). direct-edit3.jsonl:11,14,15,17,18,103 and direct-edit6.jsonl:18,23,41,73 either have no candidate within 4 pt or have one at Δ 0, so every pinned box in p6-drive3/p6-drive6 stays. Field, text and mark gestures are untouched as long as snapping is opt-in per `RectGesture`.
- **`metaKey` in `driveDirectGesture` (Q4).** `fire` builds one init for both the move and the release (1313), so `metaKey` joins `shiftKey`/`altKey` there (R11 makes it explicit). `packDrive`'s key list is scripts/drive.mjs:25 (tests seat).
- **Guide cleanup (Q4).** The ghost is removed through `options.done` on every exit: no-move (2364), `finally` (2370) and Escape (2371). Guides removed at the same three points are gone before STATE is read after `end`.
- **Chromium hit-tests `clip-path` (Q5).** CSS Masking 1 §5.1 says pointer events must not be dispatched on the clipped-out (non-visible) regions of a shape, and Blink's hit test (also used by `elementsFromPoint`) honours clip-path, so the interior of the ring misses.
- **Events from the ring (Q5).** They bubble to the button's pointerdown, click and contextmenu listeners. Those listeners test only `closest('.hit-handle')` (2786, 2803), which a ring is not, and `startRectGesture` takes the button from `currentTarget` (the button). Keyboard focus is unaffected, because `pointer-events` does not change focusability, and every path calls `button.focus()`.
- **`:hover` on the band only (Q5).** `:hover` matches the ancestors of the hovered ring, so the band hover shows the outline and handles (566, 599). The interior never hovers the button, and the `.selected` outline is on the button itself.
- **Paint order around Fm1 (Q5).** Object targets are appended before text targets (2517 then 2519-2533), and Im5 after Fm1 in scan order, so "Over" and Im5 are already above Fm1 today. With the wrapper `pointer-events:none`, even a `.selected` (z-index 2) Fm1 no longer covers them.
- **Drive clicks through the band and the interior (Q5).** `driveDirectClick` uses `elementsFromPoint[0]` (1265). On the band that is the ring: pointerdown and click bubble to the button, `focus()` on the ring is a no-op, and the gesture or click then focuses the button. In the interior it is the canvas or text layer, so the page path and `clickToAdd` (3171-3182) open the add editor exactly as the existing add-text drives do.
