# sign-merge — one signature, one door: the old "Sign…" image dialog folds into the pad

Drafted 2026-09-30 by fable51 (lean mode: one Opus 5.5 implementer + one Opus 5.5 reviewer; human-ordered in chat 2026-09-30). Line numbers are from the tree as of 2026-09-30; re-grep before editing. Rollback: `.quad/backup/pre-sign-merge-20260930.tgz`; fixture snapshot `.quad/shared/p6/checks/sign-merge-hash-before.txt` (56 lines). Baseline `npm test` = 637 tests / 636 pass / 0 fail / 1 skip. This unit builds on draw-signature: read `contract-draw-signature.md` (incl. §4 amendments), `draw-signature-build.md` and `review-draw-signature.md` first.

**Problem:** there are two doors to a signature picture. Annotate → "Sign…" (`#sign-dialog`, `src/renderer/index.html` :640-654; `openSignDialog`/`pickSignImage`/`saveSignDialog`, `src/renderer/renderer.ts` :7523-7578) asks for a name and an image file every time, remembers nothing and writes a fixed 200×60 Stamp that is not a target on the page. Fill forms → "Draw signature…" / "Sign" (draw-signature) remembers a drawing and places it with a click, but cannot take an image.

**Human decision (authoritative):**
- **H1** (2026-09-30, verbatim): "merge the old Sign… dialog into the new pad".

## Decisions (fable51; each built as written)

- **D1 (one saved signature, drawn or image)** — the pad (`#sigpad-dialog`) is the only place a signature is made. It gains `#sigpad-image` "Use an image…": the existing `api.pickImages()` picker, exactly one PNG or JPEG (the messages `pickSignImage` shows today for cancelled / too many / too large / unreadable, reworded from "signature appearance" to "signature"), decoded in the renderer with `createImageBitmap(new Blob([bytes]))` (no object URL — CSP unchanged); a file that does not decode is refused in `#sigpad-status` and nothing changes. A chosen image replaces whatever was drawn in the pad, is painted into the canvas scaled to fit (aspect kept), and enables Save; drawing a stroke or pressing Clear discards the chosen image. Save stores what the pad shows: the strokes (as today) or the image. There is still exactly one saved signature; saving one kind replaces the other; "Remove saved signature" removes either. The old dialog's **Name field is dropped**: nothing typed or personal is written with a signature any more.
- **D2 (store)** — `src/sign/drawn.ts`: the stored value becomes `DrawnSignature | ImageSignature`, `ImageSignature = { v: 1, kind: "image", width, height, data }` — `data` = the file's bytes as base64, `width`/`height` = the decoded pixel size (integers 1..16384, as the renderer measured them). `checkDrawnSignature` stays as it is for drawings (a stored value with no `kind` is a drawing — files written by draw-signature keep reading); a new exported `checkSavedSignature(value)` accepts either and is what `get`/`set` and the IPC use. Image rules: decoded byte length 1..4 MiB (`MAX_STAMP_IMAGE_BYTES`), first bytes are the PNG signature (`89 50 4E 47 0D 0A 1A 0A`) or JPEG (`FF D8 FF`), `data` is canonical base64 (re-encoding the decoded bytes gives the same string), no other keys kept; anything else → `null` (read) / refused (`set`). The original **file name is never stored** (it can be personal). The read cap rises from 4 MiB to 8 MiB (base64 of 4 MiB). File mode, temp + rename, regular-file check, `null` path = memory: unchanged. IPC channels and preload methods keep their names (`signature-get` / `signature-set`); the renderer hands the bytes over as base64 it computed. A driven or smoke session still never reads or writes the real file.
- **D3 (engine: an image signature)** — `annot-add` `signature: true` (draw-signature D1) is also accepted on `type:"Stamp"` **with** `image` and **without** `sign`: the stamp gets the image (existing `decodeStampImage`, :1791), `/Subj` = the existing `SIGNATURE_SUBJECT` ("Signature appearance"), **no `/Contents`**, no `/T`; `rect` as given (the existing Stamp rect rule); journal label "add signature". `signature` together with `sign`, on a Stamp without `image`, or on any type other than Ink/Stamp is refused before `mutate` (keep draw-signature's refusal sentence for the other types; a new sentence for the Stamp cases). The old path — Stamp + `image` + `sign:{name}` writing `Signed by <name> on <date>` — stays **byte-identical** (it is pinned by `tests/p2-annots2.test.mjs` :197-270 and used by the `--edit=shapes` smoke through `addSignature`; neither is touched).
  `annot-move` (draw-signature D2) also accepts a Stamp whose subject is `SIGNATURE_SUBJECT` (so the new image signatures **and** appearances added by the old dialog in existing documents): `point` = new top-left of its `/Rect`; optional `width` = new width, aspect kept, clamped to `[24, page width]` and so the height fits the page; rect clamped inside the page box; `annot.setRect` + `annot.update()`; journal "move signature" / "resize signature"; landing on the current rect → `noop: true`; a rect under 1 pt wide refuses `width`. Icon stamps and every other annotation keep today's refusal text verbatim.
- **D4 (placing, moving, one flow)** — `placeSignature(page, [x, y], width?)` places whichever kind is saved: a drawing as today; an image as one `annot-add {type:"Stamp", page, rect, image:{name:"signature", bytes}, signature:true, contents:""}` with `rect` = the image's aspect fitted inside `SIGNATURE_SIZE` (200×60 pt, and inside the page), or `width` wide when given (clamped as D3 clamps it), centred on the point and shifted inside the page. Same refusals, same announcement ("Added signature"), same focus on the new target, same `noteFilled()`. In Fill forms `.signature-target` is painted for drawn Inks **and** for every Stamp with `subject === SIGNATURE_SUBJECT` that is `editable`: identical gestures and keys (drag, aspect-locked handles, arrows, `+`/`-`, Delete, Escape), "Signature <n>" numbering over both kinds in page order.
- **D5 (the old door closes)** — remove `<dialog id="sign-dialog">` and all its children from `index.html`, and `openSignDialog`, `pickSignImage`, `saveSignDialog`, the `signImage` state, the six element lookups and their listeners from `renderer.ts`. Keep `addSignature` and `signatureBox` only because `smokeShapes` uses them. The Annotate button `#sign-add` **stays** (its id is in `REQUIRED_IDS`), keeps its shortcut Cmd/Ctrl+Shift+J and its label "Sign…"; its title becomes "Place your signature (a picture, not a certificate signature); Cmd/Ctrl+Shift+J"; pressing it does exactly what `#fill-sign` does (switch to Fill forms; arm placement, or open the pad first when nothing is saved). The menu keeps **one** item: "Place Signature" with accelerator `Shift+CmdOrCtrl+J` sending `{op:"sign-place"}`; the "Signature Appearance…" item and draw-signature's accelerator-less "Place Signature" item are replaced by it (`src/main.ts` :1353-1368). Renderer op `sign` with **no** contents (:1700) now behaves as `sign-place` with no contents (anything still sending it keeps working); `sign` **with** contents is certificate signing and is untouched. `OP_MODE.sign` moves to `"forms"` only if a bare `sign` needs it to switch modes — do not change the mode a contents-carrying `sign` (certificate signing) runs in; prove that with the existing `tests/drive/sign*.jsonl` staying green.
- **D6 (drive + STATE)** — `sign-draw` gains a third form: `{"cmd":"sign-draw","images":["/abs/one.png"],"contents":{"image":true}}` — `images` is the existing line-level pre-answer for `pick-images` (`src/main.ts` :1915); the op runs the pad's own "Use an image…" function and its Save (the same code path as the button), never a second one. Exactly one of `strokes`, `clear`, `image` — any two together are refused ("sign-draw: give one of strokes, image or clear"; the review's two-key refusal test is updated to this sentence in place). Refusals in `error`: no usable pre-answered image / more than one / not a PNG or JPEG the renderer can decode. `sign-place` is unchanged for callers.
  STATE, new keys only: `fill.signature.kind: "drawn" | "image" | null` (for an image `strokes` and `points` are 0); `fill.signatures[]` gains `kind: "drawn" | "image"` per entry and now lists both kinds. No existing key changes shape. The image bytes, base64 and file name never appear in STATE, a report or a log; a `sign-draw` step's `contents` stays `[redacted]` in reports (its `images` path is a scratch path the script chose and may show, as for every other `images` step).
- **D7 (tests, red before fix)** — new `tests/sign-merge.test.mjs` (helpers copied, never imported from another test file):
  (a) engine, blank page: `annot-add` Stamp + image (`fixtures/img-gray.png` bytes, read not modified) + `signature:true` → one Stamp with `/Subj (Signature appearance)`, no `/Contents`, no `/T`, the rect asked for, and an image appearance; `signature:true` + `sign` → refused, `dirty false`; `signature:true` on a Stamp without `image` → refused; the old `sign:{name}` add still writes `Signed by … on <today>` (unchanged path); `annot-move` on the image signature: `point` → rect shifted, size kept; `point` + `width` 100 → width 100, aspect kept (±0.01); `width` 5 → 24; near the page edge → inside the page; same rect → `noop: true`; `annot-move` on an **icon** stamp → today's refusal text; `annot-move` on an old-style `sign:{name}` appearance → moves (it is a signature too); `undo` reverts each.
  (b) store: image round trip in memory and in a temp-dir file (mode `0o600`), `kind` and sizes kept, no file name in the file; a drawing written in draw-signature's format (no `kind`) still reads as a drawing; refused / read as `null`: wrong magic bytes, 0 bytes, over 4 MiB, non-canonical base64, `width` 0, an extra `strokes` key alongside `kind:"image"` accepted only if ignored-and-dropped (pin whichever the code does and say so), a FIFO.
  (c) drive `tests/drive/sign-merge.jsonl`, one `test()` with `{ skip: CI_NO_ELECTRON, timeout: 180_000 }`; the test copies `fixtures/img-rgb.png` into `${OUT}` first and the script names that copy in `images`: open an `${OUT}` copy of `fixtures/hello.pdf` → `sign-draw` image → `fill.signature {saved:true, kind:"image", strokes:0, points:0}`, `dirty false`, `revision 0` → `sign-place {page:0,x:300,y:650}` → `annots.Stamp 1`, `fill.signatures` length 1 with `kind "image"`, rect centred on the point, inside 200×60, aspect = the image's → `drag` → moved → `key +` → wider, aspect kept → `sign-draw` strokes → `kind "drawn"` (the image is replaced) → `sign-place` elsewhere → `annots.Ink 1`, `fill.signatures` length 2 (one of each kind) → `key Delete` on the focused one → length 1 → `undo` → 2 → `sign` with no contents → `fill.signature.armed true` (the old menu op now arms) → `key Escape` → `armed false` → `sign-draw` with `strokes` and `image` together → the one-of error, saved signature unchanged → `mode annotate` then a step proving `#sign-dialog` is gone and `#sign-add` is present (an existing STATE key or a DOM probe the drive already offers; if none exists, assert it in (d)) → `save-to ${OUT}/merged.pdf`. The test then opens `merged.pdf` with mupdf: one Stamp with subject "Signature appearance", empty contents, no `/T`; one black Ink with subject "Drawn signature".
  (d) static (no Electron): `build/renderer/index.html` has no `id="sign-dialog"`, `sign-name`, `sign-image`, `sign-save` or `sign-cancel`; has `sigpad-image` and `sign-add`; the built `main.js` has exactly one "Place Signature" label and no "Signature Appearance…".
  Run the new test file against the pre-change build first → `.quad/shared/p6/acceptance/sign-merge-red-before.log` (≥ 1 `not ok`). ## 4. Amendments at acceptance (fable51, 2026-09-30)
- **D1/D2 (review F1): the pad keeps a re-encoded PNG, not the picked file.** `createImageBitmap` applies EXIF orientation (Electron 44.4.0, even with `imageOrientation:"none"`) but mupdf draws the stored pixels unrotated, so a phone JPEG was placed squashed and sideways. `padUseImage` now draws the decoded bitmap on an `OffscreenCanvas` (long side capped at 1000 px, `imageSmoothingQuality:"high"`), stores `convertToBlob({type:"image/png"})` and the canvas size, and closes the full-size bitmap. So: the stored `data` is always a PNG made by this app; `width`/`height` ≤ 1000; no EXIF, GPS or other metadata of the picked file reaches the store or a PDF; alpha is kept. A re-encoded PNG over 4 MiB is refused as too large (not reachable at 1000 px). Pinned by `tests/drive/sign-merge-exif.jsonl` (6 steps) and its test; red before in `acceptance/sign-merge-f1-red-before.log`. The store still accepts a JPEG written by hand into `drawn-signature.json` (D2 unchanged).
- **D3 (review F2):** `annot-move` on a signature Stamp larger than the page shrinks it to fit, aspect kept.
- **D1 (review F3):** the pad heading is "Your signature".
- **§2:** the gate's `stage()` now stages `signature.png` for the `sign-merge` drive.
