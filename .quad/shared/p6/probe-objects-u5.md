# P6 U5 gate probe — objects: rotated `cm`, duplicate splice, compound splice, box clamp (fable51, 2026-09-24)
Script `.quad/scratch/p6u5/probe.mjs` (node, built engine + `build/renderer/content-edit.js`; raw edits on a plain `mupdf.PDFDocument`, never on a session — a session write outside `mutate` throws "Can't alter an object other than in an operation"). Fixture `fixtures/p6/direct3.pdf` read only; hashes unchanged.

**P1 — rotated / flipped `cm` (decides flip/rotate/crop).** Im2's block rewritten to `q 0 60 -40 0 460 700 cm /Im2 Do Q` (90°) and to `q 60 0 0 -40 400 740 cm` (vertical flip): the scan reports `ops ['replace']`, `placement null`, `reason unsupported-transform` for both; `edit-object move` on them refuses `unsupported-transform`. `simplePlacement` (content-edit.ts:2254-2259) requires `b = c = 0`, `a > 0`, `d > 0`, and `editPlacementMatrix` (content-edit.ts:542) always emits `a 0 0 d e f` (probe: `60 0 0 40 10 10`). So flip/rotate/crop need (a) a placement rule that keeps `b`/`c` and negative factors, (b) a box model that is not an axis-aligned `[x0 y0 x1 y1]` (`editObjectBox`, content-edit.ts:526), and (c) a `Do`-relative crop (a clip before `Do` or a `/BBox` change). None exists → **deferred out of U5** (progress.md §10 keeps the candidate).

**P2 — duplicate as a byte splice.** Inserting `\nq <cm'> /Im2 Do Q` right after Im2's `Q` (`cm'` = `editPlacementMatrix(box + [10,10,10,10], [0,0,1,1])`), save, reopen: 4 objects; both `Im2` entries are candidates with `['move','resize','delete','replace']`, boxes `[400,700,460,740]` and `[410,710,470,750]`, distinct targetIds (`p0.c0.245.…` / `p0.c0.278.…`). `edit-object move` on the copy lands (`[100,300,160,340]`), the original stays; `delete` on the original keeps the copy (shared resource entry stays, as today); `undo` restores. **Ceiling proven:** the insert shifts every later placement's `token.start`, so Fm1's targetId changed (`p0.c0.309…` vs pristine) — the renderer's `resolveObject` (renderer.ts:2513: same id, else nearest of kind+name) already handles ids that change on a rewrite.

**P3 — compound splice.** Two `cm` spans rewritten in one `editSplice` (Im1 → `[80,600,180,650]`, Im2 → `[300,700,360,740]`): both land, Fm1 untouched. A 2-element `/Contents` array (split before Im2's block via `pdf.addStream` ×2) scans as `Im1 p0.c0.…`, `Im2 p0.c1.…`, `Fm1 p0.c1.…`, all candidates; `edit-object move` works in `c0` and then in `c1`, and Im2's id is stable across Im1's move (different element). So a compound op groups items by element (`record.path` `c<n>`), privatises each touched stream once, and runs one `editSplice` per stream; `editSplice` sorts by start descending and rejects overlaps (content-edit.ts:1050-1066), so an insert at `qEnd` and an earlier `cm` rewrite in the same stream coexist.

**P4 — `editObjectBox` clamp.** `[560,700,620,740]` on a Letter clip → `out-of-bounds: the box must stay inside the page`; `[552,700,612,740]` passes; a 0.5 pt side → `out-of-bounds: each side … at least 1 pt`. So the renderer translates a duplicate/multi-move back inside the page before sending (the engine keeps refusing anything that still leaves it).
