## 4. Findings

**F1 — Windows package ships a Microsoft proprietary binary, `d3dcompiler_47.dll`.** 🟡 *corrected
by investigation (m92/m95): the earlier "no notice entry, therefore Microsoft terms" reasoning is
replaced with a concrete licence finding below. Absence of a notice entry proves nothing on its
own.*
`d3dcompiler_47.dll` (4,741,488 B) is in `out/PDF4All-P0-win32-x64/`. It is the Microsoft HLSL
compiler, and **redistribution is explicitly permitted but under a proprietary licence, not an
OSS one**: Microsoft's Windows SDK [REDIST.TXT](https://learn.microsoft.com/en-us/legal/windows-sdk/redist)
(updated 10/21/2024) lists `Program Files\Windows Kits\10\Redist\D3D\{x64,x86}\d3dcompiler_47.dll`
and says the listed files' "unmodified object code form … may be copied and distributed … subject
to the software's License Terms", with "These files may only be redistributed with your Classic
Windows applications. They may not be redistributed with any Universal Windows apps." The
governing terms are the Microsoft Software License Terms for the Windows SDK. Chromium's own
docs corroborate the file coming from that SDK folder ("the d3dcompiler_47.dll file in the new
SDK attempts to dynamically link versions of the Universal C Runtime …",
`docs/windows_build_instructions.md`).
So this is a **policy conflict with the OSS-only rule that has a known licence**, not an
unknown-licence blocker and not a paid SDK: free-of-charge, but proprietary and non-OSS.
`dxcompiler.dll` / `dxil.dll` / `vulkan-1.dll` are separate questions — the first two are on the
same REDIST.TXT list yet the aggregate carries an Apache-2.0 `DirectX-Shader-Compiler` entry, so
which copy Electron ships is unresolved [?]; the Vulkan loader is covered by the aggregate's
`Vulkan Loader Components` entry.

**F1a — can it be dropped and the OS copy used? (runtime risk, evidence + unknowns).**
- ANGLE loads the compiler dynamically, so the standard Windows search order applies:
  `mD3DCompilerModule = LoadLibraryA(D3DCOMPILER_DLL_A);`
  (`google/angle` `src/libANGLE/renderer/d3d/HLSLCompiler.cpp`). With no app-local copy, the
  System32 copy is used **if present**; on failure ANGLE logs "D3D Compiler LoadLibrary failed"
  and returns `E_OUTOFMEMORY`, i.e. shader creation fails.
- Whether System32 has it is **version/patch dependent and Microsoft's own docs disagree**: the
  GDK packaging guidance says "For the HLSL compiler (`D3DCompiler`) … For Windows 10, this is
  included in the operating system. For your non-Store versions, you can include the
  `D3DCompiler_47.dll` with your game as a simple application-local file", while the older
  Direct3D 11 deployment article states the HLSL compiler DLLs "are not built into any version of
  the Windows operating system". Community reports show it present on some Win10 systems and
  absent on others. **Not safe to assume.**
- Version skew is documented: an SDK ≥ 26100 copy needs a UCRT that Windows ≤ 1909 lacks (same
  Chromium doc), so the *newer* file is the riskier one on old systems.
- If the compiler cannot load, GPU shader creation fails; Chromium's expected fallback is
  software rendering (we do ship `vk_swiftshader.dll` / `libvk_swiftshader.dylib`), and
  `app.disableHardwareAcceleration()` avoids GPU acceleration altogether. **Unverified on
  Windows** — no Windows host here and the package was never executed (F6). Our P0 UI only needs
  canvas 2D, so this is a performance question, not a correctness one.
- Options for the owner: (1) ship Electron's copy (requires explicitly waiving OSS-only for one
  Microsoft redistributable — currently not waived); (2) delete the file in the package step and
  rely on the OS copy on Win10/11, gated on a real Windows test plus a documented fallback;
  (3) delete it **and** force software rendering so the compiler is never needed, at a perf cost;
  (4) defer to the user as a scope decision. Recommendation: (2) or (3) with a mandatory Windows
  acceptance run; (1) contradicts the stated constraint.

**F2 — a bare `.app` loses Chromium's notices.** `LICENSE` and `LICENSES.chromium.html` sit
*beside* `PDF4All-P0.app` in the output directory. Whoever ships only the bundle drops 19.2 MB of
required notices. The Windows layout is safe (both files sit next to the `.exe`).

**F3 — notices live inside `app.asar`.** They are present in the distribution, but a recipient
cannot read them without `asar` tooling. Consider whether the `licenses/` folder should stay
outside the ASAR for auditability (a judgement call, not a licence requirement).

**F4 — the IJG wording duty is still unmet.** `libjpeg-README.txt` is shipped, but the IJG licence
additionally requires the sentence *"this software is based in part on the work of the Independent
JPEG Group"* in the accompanying documentation when only binaries are distributed. There is no
credits/about view in the shell at all (`build/renderer/index.html` has none), and the sentence
appears nowhere in the package. Add it with the credits screen.

**F5 — ICC status is an inference and its acceptance is still open.** The package carries
`licenses/third-party/artifex-icc-profiles.md`, which labels the four embedded Artifex ICC profiles
as an **audit inference, not a verified grant**. Nothing in this check changes that: there is still
no Artifex statement, and no one has accepted the residual risk. Recorded as unresolved.

**F6 — Windows package is statically inspected only.** It was cross-built on macOS and never
executed here, so nothing above proves runtime behaviour, GPU-path file usage, or that the
aggregate is complete for the Windows-only binaries. First-run acceptance on Windows must repeat
at least F1/F2.

**F7 — app-level licence statement.** *Superseded 2026-09-15: the user chose MIT.* `LICENSE` is at
the repo root (staged by `scripts/package.mjs` as `licenses/PDF4All-MIT.txt`) and `package.json`
says `"license": "MIT"`. At the time of this audit the package was `"license": "UNLICENSED"`
with `PRIVATE-SPIKE.txt`, which was correct for a private spike and a hard blocker for
distribution. Still open in that direction: `package-lock.json`'s root entry was not regenerated,
and the AGPL side of the bundle (`corresponding-source.md`) is not settled.
